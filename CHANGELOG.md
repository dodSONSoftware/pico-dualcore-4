# Changelog — Sensor Firmware 4

Full release notes. Each entry documents the behavior change, the wire/config impact, and what was intentionally **not** included. The "Not included" boundaries are scope decisions — do not re-propose them without a new decision.

## 0.5.0

Added transactional runtime configuration management: `config.json` is no longer a boot-time constant, it can be read and changed over MQTT as an all-or-nothing transaction without a reboot. Two new Core 0 commands on the existing command topic — `read_config` (payload must be `{}`, else `command_invalid_payload`) and `write_config` (a partial top-level patch; values are replaced as complete values, never deep-merged; empty/non-dict patch is `command_invalid_payload`) — are handled beside `reboot`. A single authoritative change-policy registry in `config.py` (`CONFIG_CHANGE_POLICIES`) maps every top-level key to exactly one of `DYNAMIC` (applied live, both cores), `RECONFIGURE` (Core 1 `devices` swap, or the single Core 0 MQTT reconnect), `RESTART_REQUIRED` (persisted, `reboot_required` set, **never auto-rebooted**), or `READ_ONLY` (`config_schema_version`, `config_generation`); the required/allowed key sets now derive from it. A successful changed transaction bumps the firmware-managed `config_generation` (new config key, `0` at boot) by one; a no-op patch (equal to the committed config — which also makes redelivery idempotent) and every failure leave the generation, the committed config, and `config.json` untouched. The committed state is a shared lock-protected `ConfigState` (committed snapshot, generation, checksum, `reboot_required`, `pending_restart_keys` — `reboot_required` is false at boot and is cleared when the pending RESTART_REQUIRED keys revert to their boot values) attached to `InterCore` so both cores read it consistently. `config_checksum_sha256` is the SHA-256 of the exact committed `config.json` bytes (never `config-secrets.json`, which never enters `config.json` — the credential boundary is preserved by not touching `load_wifi_config`). Transactions are staged, not overwritten in place: the candidate is written to `config.json.tmp`, flushed, `os.sync`ed when available, read back, fully re-validated, and checksum-compared **before** activation, then committed via the recovery-safe rename sequence (primary→`.bak`, tmp→primary, verify, best-effort delete `.bak`); a stale `.tmp` is never auto-promoted, a valid backup is restored at boot with a `configuration_recovered` event, and both-invalid fails startup clearly (no invented defaults). `read_config` returns the entire committed non-secret config plus `config_checksum_sha256`, `reboot_required`, and `pending_restart_keys` — and never `wifi_ssid`/`wifi_password`/secrets. Core 0 owns the transaction coordinator; Core 1-owned changes cross a new fourth inter-core lane, the lock-protected `ConfigTransactionMailbox` (apply/commit/rollback, one at a time, bounded `_CONFIG_TX_TIMEOUT_MS`), and a DYNAMIC interval change rebases the next deadline from *now* (prospective — invariant 10's skip policy is preserved, never a catch-up burst). `devices` reconfigure is all-or-nothing (`reconfigure_devices` retains unchanged instances by identity, builds + initializes candidates, and swaps only when every one succeeds — any failure discards all candidates and leaves the active set untouched, stricter than boot). The MQTT RECONFIGURE captures the previous connection config, re-establishes with the existing bounded handshake (no DISCONNECT into the dead link), and on failure restores + reconnects the old values; a failed restore reports `configuration_rollback_failed`. The stable response `error.code` vocabulary: `invalid_config_key`, `read_only_config_key`, `invalid_config_value`, `invalid_config_combination`, `configuration_update_in_progress`, `configuration_stage_failed`, `configuration_reconfigure_failed`, `configuration_persistence_failed`, `configuration_rollback_failed`. Observability: `configuration_update_started`/`completed`/`failed`, `configuration_rollback_completed`/`failed`, and `configuration_recovered` events carry generations, key counts, and `duration_ms` — never the patch values or secrets. `MemoryError` still propagates through every allocation-heavy path (staging, read-back, candidate device builds), and a response-delivery failure after commit never rolls the committed configuration back (the existing frozen-bytes, stamped-sequence retry carries the response). New compact `configuration` section of system information (bookkeeping only — schema version, generation, checksum, `reboot_required`, `pending_restart_keys` — never the full config or credentials) and a new `runtime_configuration` capability. Also fixed a latent import bug folded into this feature: `EVENT_CONFIGURATION_ROLLBACK_COMPLETED` was referenced on the Core 0 rollback-completed log path but never imported. `config_schema_version` bumps 8→9 (new `config_generation` key); wire/config impact is two new command names, one new config key, one new system-information section, one new capability, and the new event vocabulary; `FIRMWARE_VERSION` bumps 0.4.28→0.5.0. Not included: automatic reboot on a RESTART_REQUIRED change (an explicit `reboot` command is still the only way to activate one), runtime secret rotation or any `config-secrets.json` change, deep merge of nested patches, concurrent configuration transactions, a checksum in the health message, a generation history log, YAML/TOML or any format other than JSON, and any new thread.

## 0.4.28

Standardized the observability contract: every diagnostic log event is now `{"level": "INFO"|"WARNING"|"ERROR", "event", "reason_code", "message"?, "data"?}` — a stable lowercase_snake_case transition name, a finite canonical reason code (`"none"` for success; recovery events carry their `*_reconnect_succeeded` reason), an operator-facing message, and focused structured data — with the `module` field dropped (the domain lives in the event-name prefix), optional keys omitted when empty, and raw exception text confined to human-readable `data` (never a reason code, never a full traceback over MQTT by default). All vocabulary and one builder (`build_event_payload`) live in the new `observability.py` (module-level string constants, no classes, no registries, no dynamic event registration); every call site uses the constants. Event changes: `system_startup_completed` is renamed `runtime_started` (level `INFO`, reason `none`; `data` gains `last_reset_cause` + `boot_reason` alongside the existing one-time `startup`/`system_information` snapshots); the recovery path of `establish_network()` now emits `wifi_reconnect_completed`/`mqtt_reconnect_completed` with `wifi_reconnect_succeeded`/`mqtt_reconnect_succeeded` (the initial boot connect — including the startup self-heal re-establishment — keeps `*_connection_established`/`none`); the startup UTC pass emits `utc_sync_completed` on a clean pass and `utc_sync_failed` (reason `timeout`) before a self-heal retry; device read failures, reinitialization completions, and reinitialization failures (respecting the existing `log_failure_warning` suppression) now queue `device_read_failed` (reason `device_read_exception`; `data`: device_id, device, consecutive_read_failures, `error` as text), `device_reinitialization_completed` (reason `none`), and `device_reinitialization_failed` (reason `device_reinitialization_failed`) — one generic event with device identity as data, never baked into the event name, and a successful read still emits only telemetry; command rejections queue `command_rejected` with `command_invalid_envelope`/`command_invalid_payload`/`command_duplicate` (structured `command`/`command_id` data) and a reboot acceptance queues `runtime_reboot_requested` (reason `none`); the Core 0 liveness watchdog best-effort publishes one `runtime_core1_stalled` (reason `core1_heartbeat_timeout`, bounded QoS 1, `MemoryError` propagates, any other failure just proceeds) immediately before `machine.reset()`; Core 1's unsupported-command path emits `command_rejected` (reason `command_unknown`). Command response `error.code` values are standardized to the same canonical vocabulary with unchanged behavior: `invalid_message_schema_version`→`command_invalid_envelope`, `invalid_payload`→`command_invalid_payload`, `reboot_already_pending`→`command_duplicate`, `intercore_event_queue_full`→`command_execution_failed`, `unsupported_command`→`command_unknown`. Build identity: the common envelope gains a sixth member, `firmware_build_commit` (injected by Core 0 at publish time like the other envelope members); `version.py` reads it from a generated `build_info.py` with the dev fallback `"unknown"` (`MemoryError` still propagates, startup never blocked); `release.py` resolves the short Git HEAD (host-only, `git rev-parse --short HEAD`, ≥7 hex digits, any failure → `"unknown"`, the Pico never runs git), writes exactly one `build_info.py` into the release archive and re-opens the archive to verify its presence and exact content; `observability.py` joins `REQUIRED_FILES` (`build_info.py` deliberately does not — it is generated); the dirty-tree release policy is unchanged (the commit identifies HEAD only). `boot_reason` (startup-only, derived in `main.py` exactly once from the already-captured reset cause via `hardware.derive_boot_reason`: power_on_reset→`power_on`, watchdog_reset→`watchdog_recovery`, soft_reset→`soft_reset`, hard_reset/deep_sleep_reset/unknown→`unknown`; the values live once in `observability.py`): no flash writes, no boot history, and no `explicit_reboot` boot reason (the firmware writes no persisted evidence; the reboot command keeps its `explicit_reboot_command` reason-code face for command logs); it rides the existing hardware mailbox into the health payload and the system-information `machine` section next to `last_reset_cause` (historical/observational only — never a degraded reason). Capabilities: a new compact `capabilities` section of system information — `devices` from the `device_factory.SUPPORTED_DEVICE_TYPES` registry (supported type names, never configured instance ids, no filesystem scans) and `features` from a small static tuple of implemented capabilities only (`health`, `commands`, `mqtt_qos1`, `outage_buffering`, `network_diagnostics`, `heap_pressure_queue`) — available via the `capabilities` include section, the one-time `runtime_started` snapshot, and the system-information device; the runtime section also carries `firmware_version`, `firmware_build_commit`, `message_schema_version`, and `runtime_id` (null when not provided). Connection logs now stamp `uptime_ms`/`timestamp` at queue time (sender-owned, as command responses already are) instead of re-stamping at service time. Additive wire change (sixth envelope member, renamed/new events, new `reason_code`/`data` shapes, new health + system-information fields); `MESSAGE_SCHEMA_VERSION` intentionally stays 3 (the change is additive — consumers keyed on the old event names should migrate per the table in ARCHITECTURE.md), `CONFIG_SCHEMA_VERSION` unchanged (no config-surface change); `FIRMWARE_VERSION` bumps 0.4.27→0.4.28. Not included: connection-loss log events (recovery events only — the existing counters cover outages), per-attempt/per-retry events, queue/memory-pressure log events (counters already ride health/queues), a `command_received` event (the command response is the receipt), per-device startup initialization events (the one-time `runtime_started` snapshot covers boot), a `runtime_configuration` capability (not implemented — no runtime config, TLS, broker failover, or watchdog capability), dynamic event registration or event registries, filesystem capability scans, boot-history or flash persistence of boot reason, full Python tracebacks over MQTT, release-policy changes (dirty-tree behavior untouched), Loki or downstream pipeline configuration changes, and a schema version bump.

## 0.4.27

Added post-outage queue drain metrics and a configurable drain rate limit. Core 0 now tracks each buffered-queue drain episode: a runtime MQTT reconnect that completes successfully (`_recover_network_if_needed()` after `establish_network()`) starts an episode when `outbound_queue.get_depth() > 0` (capturing the start depth and time); an empty queue starts no episode and leaves the last completed metrics unchanged; the initial `start()` path never starts one; an in-flight entry retained across the failure participates normally; and an MQTT failure mid-drain interrupts the episode — its state is cancelled, the last completed metrics are preserved, and the next reconnect starts a fresh episode at the then-current depth. Each successful `complete_in_flight()` increments the episode count and ends it when the queue empties, freezing the five metrics: `outbound_queue_drain_active` (bool, current state only) plus the four historical scalars `outbound_queue_last_drain_start_depth`, `outbound_queue_last_drain_message_count` (completed entries, so it may exceed the start depth when Core 1 kept producing), `outbound_queue_last_drain_duration_ms` (`time.ticks_diff` from episode start to empty, including higher-priority work serviced in between), and `outbound_queue_last_drain_rate_per_sec` = `message_count * 1000 // max(1, duration_ms)` (integer-only; all five are false/0/0/0/0 before the first completed drain). The metrics live only in Core 0, ride the existing network snapshot on its existing cadence (no new mailbox, thread, or topic), and are reported in the health payload and `SystemInformation.get_queues()` with safe defaults; they are historical/observational only — a past slow drain never adds a degraded reason, never changes `status`, and never triggers a reboot. New Core 0-only setting `mqtt_post_outage_drain_rate_per_sec` (default `0` = disabled = the current unlimited drain; validated with the existing `_require_nonnegative_integer` — negative, bool, float, string, and null are rejected; `config_schema_version` bumps 7→8) optionally bounds a drain: while an episode is active and the rate is positive, only the run loop's `take()`/publish step is gated by one non-blocking next-slot tick timestamp (interval = `max(1, (1000 + rate - 1) // rate)` ms; a slot is consumed when the attempt *begins*, so a failed attempt consumes it; the first entry is eligible immediately after reconnect). The limiter never sleeps and never delays connection establishment or subscriptions, connection logs, Core 0 command/reboot responses, MQTT command polling, PINGREQ/PINGRESP, UTC handling, network probes, startup verification, or normal connected publishing; the queue's own eviction/capacity/byte policies, `Mqtt`, and `SystemInformation` are untouched, and all state is a fixed set of scalars (no lists, no per-message history, no new thread/queue/topic, no float math, all arithmetic `time.ticks_*`). Operational rule documented with the setting: the rate must exceed the normal production rate or the queue may never drain — the firmware never auto-adjusts it. Additive wire change (five new health payload fields, five new `queues` section fields); `FIRMWARE_VERSION` bumps 0.4.26→0.4.27. Not included: global MQTT publish-rate limiting, token-bucket/leaky-bucket framework classes, per-topic/per-device limits, adaptive tuning, broker load detection, queue priority/capacity/byte-budget changes, new topics or message types, persistent history, flash writes, float rate math, health degradation from the historical drain rate, or automatic reboot.

## 0.4.26

Added network diagnostics and Wi-Fi quality metrics — lightweight, observational, Core 0-owned, bounded, low-allocation, low-traffic diagnostics of Wi-Fi link quality and local-network reachability. The most important implementation rule: diagnostics observe the network without becoming a new source of network instability. `wifi.py` now owns the passive side (always on, no sockets): lifetime RSSI minimum/maximum and an integer fixed-point moving average (10 s sampling gate, valid reads only, a failed read never counts and never substitutes zero, statistics not reset on reconnect — reboot is the only reset), the full retry/backoff span of each reconnect (the initial boot connect is never a reconnect; a timer started once per disconnect sequence, not per attempt), the connect-to-IP-ready acquisition duration (association + auth + DHCP — explicitly *not* an isolated DORA exchange, the only thing this port authoritatively exposes; `ipconfig("has_dhcp4")` feature-detected once), a stable-string mapping of the WLAN `STAT_*` constants (`idle`/`connecting`/`wrong_password`/`no_ap_found`/`connect_fail`/`got_ip`/`unknown`, never raw 802.11 reason codes), the reconnect trigger (only `wifi_disconnected` / `network_probe_failure` / `unknown`), and BSSID/channel via direct STA queries only — `wlan.scan()` is never called; when a value is not authoritatively available the fields are `false`/null. The new `network_diagnostics.py` module provides the active side: `icmp_echo_supported()` (feature-detected once; expected False on RP2/cyw43 — a no-raw-socket port reports `supported=false` with null reachability and the probe is never faked with a UDP send), `probe_gateway()` (one 24-byte IPv4 Echo Request with one's-complement checksum and matching-identifier validation), and `probe_dns_server()` (one fixed 36-byte UDP query for `diagnostic.invalid.` to the configured server:53, transaction-id + QR-bit validation, any RCODE counts as reachable, never `socket.getaddrinfo()`). Every probe socket gets a finite timeout (750 ms internal constant) and is closed in a `finally`; `MemoryError` always propagates. Core 0 schedules the cycle as a staged state machine (IDLE → GATEWAY → DNS → optional BROKER): at most one bounded probe stage per run-loop pass, first cycle one full interval after Core 0 is running (never at startup), only while the network is stable (startup complete, Wi-Fi connected with a valid IP, MQTT connected — busy/recovery periods defer), a mid-cycle loss of stability discards the partial cycle without counting it, a completed cycle is counted exactly once (`network_diagnostics_run_count`, `network_diagnostics_last_run_age_ms`), all arithmetic `time.ticks_*`. The optional broker stage is gated on `network_diagnostics_broker_latency_enabled` (default `false`) AND on the QoS 1 path being completely idle (no in-flight entry, queue empty, no pending responses/logs/reboot) — busy means skip the broker stage and complete the cycle, never delay real traffic; it reuses the existing QoS 1 network-probe machinery (same client, topic, bounded PUBACK exchange, existing recovery policy) — no second recovery policy, no new probe topic. Results land in the existing shared network snapshot on its existing cadence: no new mailbox, no new thread, no new MQTT topic, and never a degraded reason (null means not-tested/unsupported and is never converted to `false`). Two new config keys, both Core 0-only: `network_diagnostics_interval_sec` (default 300; `0` disables active probes while passive RSSI sampling continues; otherwise an integer in [60, 86400]; bool/float/string/null rejected) and `network_diagnostics_broker_latency_enabled` (bool). `config_schema_version` bumps 6→7; additive wire change (ten new health payload fields — `wifi_rssi_min_dbm`, `wifi_rssi_max_dbm`, `wifi_rssi_moving_average_dbm`, `wifi_last_reconnect_duration_ms`, `wifi_last_dhcp_acquisition_duration_ms`, `gateway_reachable`, `dns_reachable`, `mqtt_broker_last_round_trip_ms`, `wifi_bssid`, `wifi_channel` — plus the corresponding `SystemInformation` network/communications section fields). Not included: continuous ping, roaming, periodic scans, spectrum analysis, history/histograms, DNS replacement, speed tests, RSSI-threshold degradation.

## 0.4.25

Restored heap-pressure-aware outbound-queue management and added runtime memory low-watermark tracking. The board's free-heap reserve (the code constants in `hardware.py`: 64 KiB Pico W, 128 KiB Pico 2 W — not config, not a heap percentage) is now the PRIMARY outbound-queue memory-safety mechanism, replacing the fixed 16-entry + 32 KiB byte budget as the admission policy. A new lock-protected `MemoryStats` object in `intercore.py` (owned by `InterCore`, passed to the queue so there is exactly one tracker) is the single shared source of the low-watermark minimum `minimum_free_heap_observed_bytes` (the lowest `gc.mem_free()` observed at an explicit checkpoint, recorded BEFORE the GC that follows it; historical/diagnostic only and never called an "absolute minimum") and of the controlled-`gc.collect()` statistics (`gc_collect_count`, `gc_bytes_reclaimed`, `gc_total_reclaimed_bytes`, `gc_last_duration_ms`, `gc_max_duration_ms` — a fixed set of scalars, no per-collect or per-message history). Admission now defends the reserve at ANY queue depth: when the current free heap is at or below the reserve, a required collect (the 1-second optional-GC cooldown is bypassed, since the reserve is a safety invariant) runs, then the oldest entry in the least-important priority class the incoming entry is at least as important as is evicted and collected again, repeating until the reserve is restored; if it cannot be restored the incoming entry is rejected and the queue is left relieved. A valid queued entry is never evicted to admit a less-important one, and the in-flight QoS 1 entry is never an eviction candidate. `gc.collect()` is never called while holding the queue lock (the lock guards queue mutation only), and a `MemoryError` from a collect propagates — it is never swallowed behind `except Exception` or retried. Controlled, conditional `gc.collect()` sits at five selected boundaries (boot, pre-Core-1, the `put()` serialization path, the Core 1 read-cycle, and the Core 0 `_publish_entry` wire-frame allocation), never on every loop, and is cooldown-gated (`CONTROLLED_GC_MIN_INTERVAL_MS`) except on the required path. The 16-entry user knob (`max_outbound_queue_entries`) and the 32 KiB `DEFAULT_MAX_OUTBOUND_QUEUED_BYTES` budget are removed from the config schema and the queue; the 16 KiB `MAX_OUTBOUND_MESSAGE_BYTES` per-message ceiling and one internal `MAX_OUTBOUND_QUEUE_ENTRIES = 64` pathological sanity guard (not a config knob) are retained. The health payload drops `outbound_max_queued_bytes` and `outbound_queue_byte_utilization_percent` (the byte view was a budget that no longer exists) and adds `minimum_free_heap_observed_bytes`; `outbound_queued_bytes` remains a diagnostic retained-payload view, `outbound_queue_pressure` is now entry-utilization-based only, and `low_free_heap` (`free_heap < reserve`) is the only heap-based degraded reason — the low-watermark minimum never degrades health. `SystemInformation.get_memory()` submits its reading to the shared `MemoryStats` (without collecting to make the numbers look cleaner) and reports the low-watermark and GC statistics; `get_queues()` reports `outbound_safety_max_entries` (the ceiling) in place of the removed byte-budget field. `config_schema_version` bumps 5→6 (the obsolete key is now rejected as an unknown key) and `FIRMWARE_VERSION` bumps 0.4.24→0.4.25.

## 0.4.24

Added a compact set of runtime-lifetime MQTT reliability metrics. The `Mqtt` class (the single source of truth) now owns five integer counters (`publish_attempt_count`, `publish_retry_count`, `puback_timeout_count`, `connection_failure_count`, `reconnect_success_count`) and two last-duration scalars (`last_reconnect_duration_ms`, `last_outage_duration_ms`); all are `0` before the first such event and reset naturally on reboot. No per-attempt lists, no unbounded history, no new thread or topic. A QoS 1 publish whose frame was fully written but whose PUBACK wait expired is now named by a dedicated `MQTTPubackTimeout` (raised by `mqtt_client.publish()` from a timeout-errno classified read) and counted precisely in `puback_timeout_count` — a stalled PUBLISH frame *write* stays an ordinary publish failure and is never counted as a PUBACK timeout. A retry of the same logical message is classified by Core 0 (the owner of logical message identity, via the persistent in-flight entry / command-response / reboot container) and passed to `Mqtt` explicitly as `is_retry` — never inferred from packet id, topic, payload, or time. `Mqtt.status()` is the authoritative read interface; Core 0 copies the seven values (canonical `mqtt_*` names) into the network snapshot, which `SystemInformation.get_communications()` and the health payload both report (integer zero when the snapshot is older/incomplete). The metrics are historical/diagnostic only: they never add a degraded reason or change `status` (the current-state rules remain the only source of degraded reasons). The `mqtt_connection_established` reconnect log gains `reconnect_success_count`, `reconnect_duration_ms`, and `outage_duration_ms`. Reconnect/outage durations use `time.ticks_*` (wrap-safe) and are not restarted by individual attempts or repeated `mark_disconnected()` calls. Additive wire change (seven new health fields, seven new communications fields, three new reconnect-log fields); no `config_schema_version` change.

## 0.4.23

Added the last reset cause to runtime diagnostics. `machine.reset_cause()` is now read exactly once at startup — `main()`, immediately after `detect_hardware()` — and translated by the new `hardware.read_last_reset_cause()` into a stable firmware-facing string (`power_on_reset`, `hard_reset`, `watchdog_reset`, `deep_sleep_reset`, `soft_reset`, or `unknown`; the raw MicroPython integer is never published). The value is stored in the startup hardware snapshot, which `main()` publishes to the hardware state mailbox before any Core 0/Core 1 operation begins, replacing the Core 1 startup re-publication that re-derived a snapshot from `get_machine()` and overwrote the mailbox; both consumers now read the one immutable snapshot. The health payload carries `payload.last_reset_cause`, and the system-information `machine` section carries the same field (sourced from the snapshot, never re-read from `machine`). A read failure degrades the field to `"unknown"` instead of failing startup; a `MemoryError` still propagates. The reset cause is historical diagnostic information: a previous `watchdog_reset` (or any other cause) must never add a degraded reason or change `status` from `healthy`. Additive wire change (one new health field, one new machine-section field); no `config_schema_version` change.

## 0.4.22

Made the 16 KiB per-message ceiling a queue invariant on both admission paths, not just a property of the `put()` serialization path. `put()` enforces it via `serialize_and_validate_message()` (a `MessageTooLargeError` rejection), but `put_with_kind()` — the pre-serialized-bytes path both production callers (startup log, health message) use — passed bytes straight to `_admit_locked()` with no per-message size check: the 32 KiB aggregate byte budget therefore admitted a single entry of up to 32 KiB through that path, invalidating the 16 KiB transient-peak rationale (graph + str + bytes ≈ 3x the payload ≈ 48 KiB) both memory bounds are sized against. Both shipping callers serialize first and were safe, so this closed an invariant gap (two sources of truth for the memory rule) rather than a live defect. `put_with_kind()` now rejects any payload longer than `MAX_OUTBOUND_MESSAGE_BYTES` — the same constant `put()` enforces — incrementing the existing `oversized_rejected` counter and leaving queue state untouched, exactly like the `put()` path. No re-parsing or JSON allocation (a length check on final bytes), and the caller contract (bytes are already validated, serialized JSON) is unchanged. Failure-path behavior change (no `config_schema_version` change).

## 0.4.21

Made the outbound byte budget account for the in-flight entry's retained bytes, so the budget now caps ALL payload bytes the outbound queue retains, not just the queued FIFO. The in-flight entry is popped out of the FIFO by `take()` and held until its PUBACK (`complete_in_flight`), so its payload bytes stay resident the whole time — but `take()` subtracted them from the byte count the moment the entry moved in-flight and `complete_in_flight()` never re-added them. The budget therefore capped only the queued FIFO: a 16 KiB in-flight payload plus a full 32 KiB of queued payloads could be resident at once (48 KiB) while `outbound_queued_bytes` reported only 32 KiB, and admission kept granting the full 32 KiB of queued room on top of whatever was in flight. Now `take()` leaves the entry's bytes counted, `complete_in_flight()` releases exactly the completed entry's bytes, and eviction subtracts queued entries as before — the in-flight payload consumes budget for as long as it is retained. This tightens the worst-case retained payload from 48 KiB to 32 KiB and makes the two budget views consistent: `outbound_queue_depth` already included the in-flight entry, and `outbound_queued_bytes` now does too. `outbound_queued_bytes` (health and startup log) can now read slightly higher while an entry is in flight; `outbound_max_queued_bytes` is unchanged. Steady-state memory-boundary change (no `config_schema_version` change).

## 0.4.20

Made a Core 0 command/reboot response retry the same wire document, not just the same sequence identity. 0.4.17 made `(runtime_id, sequence)` a reliable unique event identity by claiming the sequence before the first transmission attempt and stamping it on the logical object so a retry reuses it — but for Core 0's own retryable responses (the pending command responses and the pending reboot) the identity was preserved while the *content* was not: `_publish_core0_command_response()` rebuilt the message (re-capturing `uptime_ms` and `timestamp`) and re-serialized it on every attempt, so an ambiguous QoS 1 failure (the PUBLISH reached the broker but the PUBACK was lost) followed by a retry put two packets with the *same* `(runtime_id, sequence)` on the wire carrying *different* documents (differing `uptime_ms`/`timestamp`). A downstream deduplicator keyed on that identity could then discard one of two differing documents depending on arrival order. Queued telemetry never had this problem because its pre-serialized bytes stay attached to the same in-flight queue entry. The serialized bytes are now frozen on the persistent logical object on the first attempt (a new `container` parameter on `_publish_core0_command_response()`, the pending response dict or the pending reboot dict, mirroring the queue's in-flight entry) and re-published verbatim on a retry, so a retry is the same logical message with the same identity AND the same content. The wire format and the QoS 1 at-least-once guarantee are unchanged; only the pathological ambiguous-failure-then-retry case now emits byte-identical frames. Failure-path behavior change (no `config_schema_version` change).

## 0.4.19

Made the disposal of a failed MQTT client bounded too, closing the last unbounded write on Core 0's network path. 0.4.16 bounded the QoS 1 PUBLISH frame writes and the PUBACK wait, but the cleanup of the client left behind after such a failure was not: `Mqtt._close_old_client()` — the first step of every `connect()` attempt, i.e. of every reconnect — called `MQTTClient.disconnect()`, which unconditionally wrote an MQTT DISCONNECT frame. After a failed bounded exchange, the exchange's `finally` had already restored the socket to infinite-blocking mode, so that DISCONNECT write into the already-failed link had no deadline: on a blackholed link (TCP up, sends not draining) it wedged Core 0 inside `sock.write()` forever, and with Core 0 wedged its Core 1 heartbeat watchdog (0.4.9) could never run either — the same P1 class 0.4.16 fixed for the PUBLISH itself, one step later in the failure chain (publish stalls → bounded timeout → socket restored to infinite blocking → reconnect → unbounded DISCONNECT write → permanent wedge). Disposal now closes the TCP socket directly with no write at all: this path only ever runs while the session is not connected (`connect()` is only entered from `establish_network()`'s `while not is_connected()`), so the old client is always failed or never established and no graceful DISCONNECT frame is needed — the broker drops the clean session when the TCP connection closes. Failure-path behavior change (no `config_schema_version` change).

## 0.4.18

Made the queued-byte budget visible to system telemetry and health, so the queue's memory-protection boundary can no longer be full while health reports no pressure. The byte budget (0.4.8: 32 KiB of queued payload bytes, enforced alongside the 16-entry count) was only ever reported as entry counts: `SystemInformation.get_queues()` (the startup-log source) and the health payload both carried no byte view, and `outbound_queue_pressure` was computed from entry utilization alone — a handful of large entries (e.g. 4 × ~8 KiB) could sit at 25% entry utilization while the byte ceiling was at 100%, the exact condition the budget exists to flag. The health payload now carries `outbound_queued_bytes`, `outbound_max_queued_bytes`, and `outbound_queue_byte_utilization_percent` (sourced from a new single-lock `OutboundQueue.get_health_metrics()` reading both budget views consistently), `SystemInformation.get_queues()` now exports the two byte fields, and `outbound_queue_pressure` fires at `max(entry_utilization, byte_utilization) >= 75%`. Queued bytes exclude the in-flight entry, matching the byte admission budget in `_admit_locked`; the entry-depth field still counts it, as before. The byte-utilization computation is integer-only (MCU-safe), no new config or schema surface. Additive wire change (three new health payload fields); no `config_schema_version` change.

## 0.4.17

Made the wire `sequence` reliable across an ambiguous QoS 1 failure. The sequence was consumed only after a successful PUBACK, so in the ambiguous case — the PUBLISH reached the broker but the PUBACK was lost — the number was never consumed and was handed out again: a `mqtt_connection_established` log published after the reconnect took the in-flight telemetry's sequence (a `(runtime_id, sequence)` collision on the wire), and the telemetry retry then took a still-newer one, so the same logical sample appeared under two identities and an unrelated message reused the sample's number. The sequence is now claimed before the first transmission attempt and stamped on the logical object — the queue entry, or Core 0's persistent response/reboot dict for its own retryable messages (`_claim_wire_sequence` in `core0.py`) — and is never rolled back: a retry of the *same* logical message reuses the stamped number (both copies identify one message, legitimate QoS 1 duplicate delivery), while a *different* message always gets a fresh number. `(runtime_id, sequence)` is therefore now a safe unique event identity and a retry is recognizable as the same message. The wire format is unchanged (same top-level keys, same Core 0 values) and the QoS 1 at-least-once delivery guarantee is unchanged. Failure-path behavior change (no `config_schema_version` change).

## 0.4.16

Bounded the QoS 1 PUBLISH frame writes, not just the PUBACK wait. `MQTTClient.publish()` installed the socket timeout only *after* all four socket writes (header, topic, packet id, payload), so a link failure that leaves TCP apparently established while sends stop making progress wedged Core 0 inside `sock.write()` — and with Core 0 wedged, its Core 1 heartbeat check (the 0.4.9 watchdog) never ran, leaving no recovery path. The timeout is now installed before byte 1 of the frame and restored only after the exchange finishes, so the frame writes and the PUBACK wait share one bounded deadline: a stalled write surfaces as a bounded error into `Mqtt.publish_qos1`'s disconnect + network recovery (the entry stays in flight, at-least-once semantics unchanged). Wire order (header, topic, packet id, payload) and the QoS 0 path are unchanged; a failed timeout installation now aborts before any byte is transmitted instead of after the full frame. Failure-path behavior change (no `config_schema_version` change).

## 0.4.15

Made `MemoryError` propagation consistent on the Core 0/Core 1 message paths. Heap exhaustion is a fatal condition, not a failed optional diagnostic, but several allocation-heavy paths swallowed it in a generic `except Exception` handler and kept the core running on top of an exhausted heap: `core1._collect_system_information_full()` (a failed section was recorded as `{"error": ...}`), `core1._try_queue_startup_log()` and `core1._try_queue_health_message()` (the message was silently discarded as if serialization had merely failed), `core1._build_health_payload()` (heap/hardware fallbacks), the Core 1 startup hardware storage, `core0._service_pending_connection_log()`, and `core0._publish_core0_command_response()` (whose handler was `except (MessageTooLargeError, Exception)` — effectively `except Exception`). Every one of these now re-raises `MemoryError` before the generic handler, matching the convention every other module already followed. Heap exhaustion now stops the core with a diagnosable error instead of obscuring the root cause or making fragmentation worse, and the callers' existing `except MemoryError: raise` clauses (e.g. `_perform_reboot`) can now actually fire. Ordinary (non-`MemoryError`) failures are still handled as before: reported and the message discarded. Failure-path behavior change only (no `config_schema_version` change).

## 0.4.14

Stopped the telemetry scheduler from replaying missed boundaries as catch-up reads. When a device read stalled long enough to cross one or more `read_loop_sec` boundaries, the deadline advanced by a single interval per pass, so the loop fired an extra read almost immediately — and another, until it caught up: a burst of near-identical current samples, JSON work, and queue admissions landing right after the overload. Telemetry is a current sample, not a replayable record, so a stall cannot reconstruct the missed samples; the scheduler now performs the current sample once and skips directly to the next future boundary — the same missed-boundary policy the health scheduler already used. The skip is evaluated against a clock re-read after the read completes, because the loop's captured clock is stale by however long the read took and would otherwise under-advance and leave a catch-up read for the next pass. Outage buffering is unchanged (an MQTT outage still queues telemetry rather than dropping it); this only changes the pathological slow-read case. Static behavior change (no `config_schema_version` change).

## 0.4.13

Eliminated the double serialization on the publish path. A queued message was serialized by its sender and then, on Core 0, decoded, parsed back into a dict, merged with Core 0's envelope fields, and re-serialized as a whole document (`dict → str → bytes → queue → str → dict → str → MQTT`): the message body was serialized twice, and the transient allocations, CPU, and fragmentation risk accumulated exactly where the queue was supposed to improve memory predictability. The contract is now: the sender carries its complete message — including `uptime_ms` and `timestamp` (null when UTC is unsynchronized) — and must not carry any envelope key at the top level (`sequence`, `runtime_id`, `source`, `firmware_version`, `message_schema_version`); Core 0 injects those five members at publish time by splicing them into the stored serialized object before its closing brace. The payload is never decoded, parsed, or re-serialized on the publish path, so publishing allocates only the small envelope fragment plus the assembled frame. The wire format is unchanged (same top-level keys, same Core 0 values) and the queue still stores immutable pre-serialized bytes — the frame is a fresh allocation, the entry is untouched. Core 1 no longer pre-embeds `runtime_id`/`source`/`firmware_version`/`message_schema_version` (they were always overwritten by Core 0 anyway), and the health/startup-log `timestamp` is computed from the shared UTC snapshot instead of being left null for Core 0 to fill (which required the parse it could no longer afford). Static behavior change (no `config_schema_version` change).

## 0.4.12

Bounded the inbound MQTT packet size. `wait_msg()` now rejects a PUBLISH whose remaining length exceeds `MAX_INBOUND_PACKET_BYTES` (16 KiB — the same MCU-scale ceiling as the outbound limit) *before* allocating its payload: previously `sock.read(sz)` was handed whatever the broker's remaining-length field claimed, and a broker-side bug publishing an oversized command/info response could request an allocation large enough to exhaust the Pico W's RAM (no hostile traffic required). An oversized frame — like a fifth remaining-length byte (an MQTT protocol violation that was previously an unbounded read loop) — now closes the socket and raises `MQTTException`, which the `Mqtt` layer turns into a marked disconnect and Core 0's existing recovery path reconnects, instead of trying to buffer or drain the corrupt stream. Static constant (no `config_schema_version` change).

## 0.4.11

Fixed the MQTT receive path parsing incoming packets in non-blocking socket mode. `check_msg()` now decides *readiness* with a non-blocking `select` poll — one readable byte means a packet has started; nothing returns `None` immediately and leaves the socket mode untouched — and only then parses the packet on a blocking-with-finite-timeout socket bounded by `mqtt_broker_response_timeout_sec`. Previously the whole multi-byte parse ran non-blocking, and because MicroPython documents that `read(n)` may return fewer bytes than requested in non-blocking mode, a PUBLISH split across TCP reads could short-read its topic or payload and deliver a corrupt frame (or raise a spurious disconnect) instead of waiting for the rest of the packet. Now a link that stalls after the first frame byte surfaces as a bounded timeout into the existing recovery path, and a ready packet is always fully read. `wait_msg()` and the bounded-wait invariants are otherwise unchanged; `check_msg()` now installs and restores its own finite timeout like `publish`/`ping`. Static behavior change (no `config_schema_version` change).

## 0.4.10

Made startup verification self-healing to match the (already) unbounded connect loops. Previously the QoS 1 probes and UTC sync were the only fail-fast steps: a single transient blip after connection — a dropped PUBACK on a probe, or a brief UTC-server outage across the 3 bounded attempts — raised `RuntimeError` out of `core0.start()`, exited `main()`, and left the device stopped until a physical reset, even though a broker that was *never* reachable would have looped forever. `start()` now keeps the verification steps (probe #1 → drain → 5 s wait → probe #2 → UTC) in a new `_verify_startup_contract()` pass inside a retry loop: on any pass failure it drops the MQTT session (`mark_disconnected()`), re-establishes the network, and retries the whole pass, reusing the existing `mqtt_reconnect_delays_sec` backoff. Core 1 stays gated because `start()` has not returned and `_network_stack_ready` is set only after a clean pass; a `MemoryError` still propagates (fail-fast) so an out-of-memory device is not looped. Static behavior change (no `config_schema_version` change).

## 0.4.9

Core 0 became the independent consumer of the Core 1 liveness heartbeat, closing the P1 failure mode where a dead or wedged Core 1 thread (an unhandled `MemoryError`/`Exception`) wedged the whole sensor — telemetry and health silently stopped, a dead Core 1 could not build the health message that would report `core_1_inactive`, and Core 0 kept running indefinitely with no recovery. The Core 0 run loop now checks `core_1_activity_ms` first on every pass (`_watch_core_1_heartbeat` in `core0.py`): before any stamp exists (Core 1 has not started) the check is a no-op, so the unbounded startup connect loops are unaffected; once a stamp exists, age at or beyond `_CORE_1_HEARTBEAT_STALE_TIMEOUT_MS` (30 s — more than six missed 5 s refreshes, and below the 60 s `core_1_inactive` diagnostic threshold) logs FATAL and calls `machine.reset()`. Static constant (no `config_schema_version` change).

## 0.4.8

Made the outbound message/queue limits MCU-safe. The per-message ceiling dropped from 128 KiB to 16 KiB (`message_serializer.MAX_OUTBOUND_MESSAGE_BYTES`) — the check runs after `json.dumps()` + UTF-8 encode, so the object graph, serialized `str`, and encoded `bytes` are all resident at once and a 128 KiB payload could not be admitted safely on a Pico W; 16 KiB bounds a single message's transient peak (~48 KiB) with margin over the largest legitimate message (the startup log). `OutboundQueue` is now bounded by BOTH entry count and an aggregate queued-byte budget (`DEFAULT_MAX_OUTBOUND_QUEUED_BYTES` = 32 KiB), so 16 retained payloads can no longer exhaust heap on their own; admission enforces both budgets and only evicts when it frees enough room (by count or bytes), never dropping a valid entry to admit one that would not fit. Both bounds are static constants (no `config_schema_version` change); `OutboundQueue.status()` now also reports `queued_bytes` and `max_queued_bytes`.

## 0.4.7

Fixed the MQTT handshake blocking indefinitely: `Mqtt.connect()` now passes `mqtt_broker_response_timeout_sec` to `MQTTClient.connect()`, bounding the CONNACK wait — and, since `subscribe()` inherits that socket timeout, both SUBACK waits. A broker that accepts the TCP connection and then stops responding now fails the connect attempt (retried with the reconnect backoff) instead of wedging Core 0 forever; the socket returns to normal blocking mode once both subscriptions succeed.

## 0.4.6

One shared normal-runtime scheduling epoch for all periodic Core 1 work. `normal_runtime_start_ticks_ms` is captured exactly once, immediately after `system_startup_completed` is admitted to the outbound queue; both the telemetry deadline (`anchor + n × read_loop_sec`) and the health deadline (`anchor + n × health_interval_sec`) derive their fixed boundaries from that anchor. Telemetry and health remain independent schedulers (shared epoch, no execution dependency); neither deadline derives from the other. `boot_ticks_ms` remains the boot-lifetime reference for uptime (`uptime_ms`) and startup-duration measurement only. Reconnects, UTC resyncs, and device reinitialization never reset the anchor; only a reboot creates a new one. Health outage policy is unchanged (missed intervals skipped, never replayed); telemetry outage buffering is unchanged.

## 0.4.5

Health scheduling anchored to boot time: `health_interval_sec` now defines fixed uptime-based boundaries from firmware boot (60s interval → first health at ~60s uptime, then 120s, 180s, ...). The immediate post-startup health message is removed; boundaries missed during startup or an MQTT outage are skipped, never replayed; deadlines advance from the previous boundary so processing delay cannot accumulate drift.
