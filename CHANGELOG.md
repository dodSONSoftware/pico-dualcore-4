# Changelog

This document records notable changes to the project across released versions.

Changes are organized by version in reverse chronological order, with the most recent release listed first. Each version should summarize meaningful changes such as new features, fixes, behavioral changes, refactoring, configuration changes, and other updates relevant to developers or operators.

## Versioning

Project versions follow Semantic Versioning where practical:

- **MAJOR** — incompatible or breaking changes
- **MINOR** — backward-compatible features or significant enhancements
- **PATCH** — backward-compatible fixes, maintenance, and small improvements

## Change Categories

When applicable, changes should be grouped under clear categories such as:

- **Added**
- **Changed**
- **Fixed**
- **Removed**
- **Deprecated**
- **Security**

## Version History

- **Unreleased** (firmware 0.4.52): **Fixed a configuration advertised as hot-reloadable that only takes effect on the next boot** — `network_probe_timeout_sec` is now `REBOOT_REQUIRED`, restoring the ACTIVE-vs-PERSISTED contract.
  - **The network probe timeout is no longer misclassified HOT** (`config_manager.py`, `core0.py`): the policy table declared `network_probe_timeout_sec` `HOT_RELOADED` and Core 0 carried it in its live hot-apply set, but its only consumer is the startup verification contract's network probes — there is no steady-state probe — so a write could answer `classification: HOT_RELOADED` / `reboot_required: false` for a value with no effect on the running system (it took effect only on the next boot). The key is now `REBOOT_REQUIRED` and removed from `_HOT_APPLY_CORE0_KEYS`; no runtime change was needed. The HOT set is now exactly the two live apply sets: Core 0's four (`datetime_sync_interval_min`, `mqtt_command_poll_ms`, `mqtt_outbound_publish_delay_ms`, `network_snapshot_interval_sec`) plus Core 1's two (`read_loop_sec`, `health_interval_sec`).
  - New tests in `tests/test_config_manager.py`: the classified-HOT set must equal exactly `_HOT_APPLY_CORE0_KEYS | _HOT_APPLY_CORE1_KEYS` (HOT_RELOADED promises a live effect, so a key no steady-state runtime consumes can never be HOT), and `network_probe_timeout_sec` classifies a probe-only change as `REBOOT_REQUIRED`.

- **Unreleased** (firmware 0.4.51): **Fixed an unsupported inbound MQTT frame reaching the application before its rejection** — inbound PUBLISH QoS is now validated from the opcode byte, before the payload is read and before the callback (which feeds the command protocol) can run.
  - **Inbound QoS profile is enforced at the wire layer** (`mqtt_client.py`): `wait_msg()` delivered the payload to the callback and only then rejected an inbound QoS 2 PUBLISH — so a nonconforming MQTT peer could carry a `write-config` / `reboot` / `get-details` frame into the command protocol before the MQTT layer announced the rejection — and a QoS 3 PUBLISH (invalid by the MQTT spec) reached the callback and fell through with no rejection at all. The QoS bits are now checked on the opcode byte, before the remaining length, topic, or payload is read: QoS 2 and QoS 3 both drop the connection through `_abort_corrupt_inbound` (socket closed, `MQTTException` raised, Core 0's recovery reconnects) with the callback never invoked and no payload allocated; only QoS 0 and QoS 1 (PUBACK-acknowledged) are delivered.
  - `tests/test_mqtt.py`: the inbound QoS 2 regression test now asserts the callback received nothing and the socket was closed, and a new test pins the same pre-callback rejection for an invalid QoS 3 PUBLISH.

- **Unreleased** (firmware 0.4.50): **Fixed timing configurations exceeding MicroPython's usable tick interval** — ticks-backed timing values now carry the RP2 ticks delta ceiling in config validation.
  - **Ticks-backed intervals are bounded by the ticks delta ceiling** (`config.py`): nearly every timing value was validated only for type/sign, but the RP2 builds give `time.ticks_*` 30-bit tick values, so `ticks_add()`/`ticks_diff()` only express deltas below half the period — `2^29 - 1` ms (about 6.21 days), and `ticks_add` raises `OverflowError` at half the period. Above the ceiling the failure was silent or fatal per field: a huge `mqtt_command_poll_ms`/`mqtt_outbound_publish_delay_ms`/`network_snapshot_interval_sec`/`datetime_sync_interval_min` made a `ticks_diff >= threshold` check that could never be true (command polling, the pacing gate, network snapshots, or UTC re-syncs stopped permanently after the first event), while an excessive `read_loop_sec`/`health_interval_sec`/`mqtt_broker_response_timeout_sec` reached `ticks_add` (scheduler re-anchor, deadline) with an illegal delta and raised `OverflowError`. Because mixed candidates containing any reboot-required change persist without runtime application, the invalid value would survive validation and fail only on the next boot. `validate_config()` now rejects any of `read_loop_sec`, `health_interval_sec`, `network_snapshot_interval_sec`, `mqtt_broker_response_timeout_sec` (> `536870`), `datetime_sync_interval_min` (> `8947`), `mqtt_command_poll_ms`, or `mqtt_outbound_publish_delay_ms` (> `536870911`) with a stable `invalid_value` code naming the per-field maximum, so both startup and write-config reject it. Socket-timeout-only values (reconnect delays, probe timeout, the sliced retry delay) do not use ticks deltas and remain unbounded. The ceiling is the absolute safety bound, not a new application limit: `MAX_TICKS_SAFE_INTERVAL_MS = (1 << 29) - 1`.
  - New tests in `tests/test_config.py`: per-field boundary acceptance/rejection at the per-unit maximum and first-rejected value (with the stable code and per-field maximum in the message), zero `mqtt_outbound_publish_delay_ms` staying valid, and two more rejection-matrix cases.

- **Unreleased** (firmware 0.4.49): **Fixed a valid configuration making MQTT permanently unable to connect** — `mqtt_keepalive_sec` now carries its real boundary in config validation.
  - **`mqtt_keepalive_sec` is bounded by the MQTT wire limit** (`config.py`): `validate_config()` only required a positive integer, while the transport independently rejects anything above 65535 (MQTT 3.1.1 encodes Keep Alive as a 16-bit word) inside `MQTTClient.connect()`. Because the key is `REBOOT_REQUIRED`, a remote `write-config` could persist 65536 and report success with `reboot_required=true`; after the reboot Wi-Fi connected, every MQTT attempt threw the keepalive validation, and `establish_network()` retried forever — Core 1 never started and the MQTT command channel needed to repair the configuration never came up. The boundary check now lives in `config.py` (`MAX_MQTT_KEEPALIVE_SEC = 65535`, stable `invalid_value` code) so both startup and write-config reject it, and the `mqtt_client.py` check remains as defensive transport validation.
  - New tests in `tests/test_config.py`: 65535 accepted and 65536 rejected with the stable code and exact message (plus a `invalid_value` case in the rejection matrix).

- **Unreleased** (firmware 0.4.48): **Fixed three wait/queue-semantics issues** — configured zero delays are now immediate retries instead of silent 100 ms waits, an append whose own allocations cross the heap reserve can now displace a queued lower-priority entry instead of being rejected while that entry stays retained, and the outbound depth high watermark now counts the in-flight entry like the depth metric does.
  - **Zero delays no longer wait** (`wifi.py`, `mqtt.py`, `core0.py`): the three interruptible-wait loops floored their slice count at one (`max(int(delay * 10), 1)`), so a configurationally valid zero delay (reconnect delays permit zero) waited 100 ms and ran one watchdog/servicing pass it was never asked to run. A `delay <= 0` now returns immediately: no slice, no servicing, clock unadvanced — an immediate retry, as configured. Positive delays are unchanged (each 100 ms slice still services the wait hook, so the Core 0 heartbeat watchdog still fires inside them).
  - **Append-crossed admissions join the displacement path** (`intercore.py`): when the fast-path append's own allocations crossed the heap reserve, the undo was immediately rejected as transient — even for a CRITICAL admission while a HEALTH entry sat queued. Now the undone append is fed into the same priority-displacement decision: an eligible less-important queued entry is evicted for it (reclaim, re-measure, repeat), and only when nothing eligible remains is the admission rejected as transient. The priority rule is unchanged — a lower-priority incoming entry is still rejected while a more important queued entry is retained, and the in-flight entry is still never a displacement candidate.
  - **The depth high watermark counts the in-flight entry** (`intercore.py`): the watermark was measured against the FIFO length only, while `depth` is queued + in-flight, so a runtime state of depth 2 could carry a historical peak of 1. The watermark now uses the same retained-entry definition as the depth metric, so the peak can never be below the current depth (`_high_watermark_bytes` already tracked the retained-bytes metric the same way).
  - New tests: `tests/test_network_wait_service.py` (zero-delay Wi-Fi and MQTT waits wait and service nothing; positive-delay servicing preserved), `tests/test_core0_heartbeat_watchdog.py` (zero-delay `_sleep_and_service` resets nothing with a stale stamp armed; a positive delay still resets on its first slice), `tests/test_intercore.py` (append-crossing displaces a lower-priority entry and keeps its priority rejection rule; the watermark-at-least-depth invariant asserted across the queue lifecycle, including the in-flight-admission case).

- **Unreleased** (firmware 0.4.47): **Fixed a valid configuration permanently failing startup** — an oversized detailed startup log no longer wedges Core 1 into a reset loop; when the only problem is that it exceeds the 16 KiB outbound ceiling, Core 1 now admits a bounded fallback summary and startup continues.
  - **The startup log gained a bounded fallback** (`core1.py`): device definitions carry no practical length or count bound for `id`, `name`, or `sensor_type`, so the detailed `system_startup_completed` log could exceed `MAX_OUTBOUND_MESSAGE_BYTES` on an otherwise valid configuration. `_try_queue_startup_log()` treated that `MessageTooLargeError` as a generic permanent rejection, so Core 1 halted, Core 0's liveness watchdog reset, and the same configuration reloaded — an unbootable loop caused purely by the diagnostic artifact. Now the size case alone raises `StartupLogTooLargeError` (a `ValueError` subclass), and `core1_main()` answers it with the bounded fallback summary — the same startup statuses and device counts, but no `ready_devices[]`/`failed_devices[]` and no `system_information` — which stays far under the ceiling, keeping the invariant that failure to emit the verbose diagnostics must not prevent the device from entering normal operation. Every other permanent rejection (validation, serialization) still fails fast with its actual reason, and both the detailed message and the fallback keep the single-transient-retry admission discipline.
  - New tests in `tests/test_startup_log.py`: the bounded builder drops the unbounded sections; the size case raises the typed error without reaching the queue; a size-only rejection is answered by admitting the bounded summary; a non-size permanent rejection escapes without ever building the fallback; and a transient rejection of the fallback keeps its single retry.

- **Unreleased** (firmware 0.4.46): **Fixed the publish-path and admission boundaries so a message that can never be published, or a command whose acknowledgement cannot be reserved, no longer wedges the channel or silently swallows side effects.**
  - **Core 0 command admission is now conditioned on being able to answer** (`core0.py`): a command is refused — before its `command_id` is claimed and before any execution — when its response slot cannot be reserved (a full 4-slot pending queue), leaving the side effects unapplied (write-config does not promote, reboot does not arm) and the ID unclaimed so an application-level retry redelivers once capacity frees up. Previously the command could execute and then lose its acknowledgement to a full response queue, after which the sender's retry was suppressed by the debounce cache — the command ran, the answer never arrived, and no retry could recover it. A pending HOT_RELOADED update holds one slot too: its response is queued later, at Core 1's acknowledgement, so a new admission can no longer overrun the deferred acknowledgement.
  - **The publish-path envelope splice is now size-bounded before it allocates** (`core0.py`, `intercore.py`, `message_serializer.py`): the body is admitted at or under `MAX_OUTBOUND_MESSAGE_BYTES`, but the spliced Core 0 envelope is added on top of it, so `_publish_entry` checks the *final* wire length (body + comma + fragment + closing brace) against the ceiling before `bytes.join()` runs and raises `OutboundMessageTooLargeError` (a `ValueError` subclass) if it would exceed it. The failure is permanent for the entry (its bytes are fixed), so it is handled per kind: a command response is answered with the bounded `response_too_large` substitute (the FIFO keeps moving instead of stalling on unsendable bytes), and telemetry/health/log entries and connection logs are dropped with a warning — never held in flight and never retried. The queue counts these separately as `oversized_discarded` (distinct from admission-time `oversized_rejected`).
  - **A permanently unsendable command response is replaced by a bounded substitute** (`core0.py`): a permanent serialization failure recorded on the response (`_permanent_failure`) is answered with the small bounded error response whose `error.code` states the cause (`response_too_large` / `response_invalid`) — the same policy Core 1 applies at admission — while a transient QoS 1 failure still leaves the original pending for retry. Previously a permanent failure was re-submitted every pass, blocking every response behind it.
  - **`mqtt_client.py` runtime `assert`s are gone** — all ten were replaced with explicit parameter validation raising `MQTTProtocolError` (asserts vanish under MicroPython `opt ≥ 1`, turning a protocol violation into a silent skip). Outbound QoS 2 is now rejected before a single frame byte is built.
  - **The device-initialization retry sleep no longer ages the liveness stamp** (`device_manager.py`): `device_initialization_retry_delay_ms` is unbounded, so a monolithic `time.sleep_ms()` would age the stamp past Core 0's watchdog bound for a sufficiently long configured delay and cause a false reset. The retry sleep (both the initialization and reinitialization paths) now runs in steps of at most 100 ms, refreshing the liveness stamp at each step boundary.
  - **A failed write-config promotion restores the committed config before the failure propagates** (`config_manager.py`): new `_restore_committed()` puts `config.json.old` back over the promoted file (and clears the failed `.tmp` candidate) when the first promotion rename has already moved the committed config into `.old`, so `config.json` is never missing when the caller regains control; the original failure still propagates unchanged and every recovery artifact stays for boot recovery.
  - New tests: `tests/test_command_admission_capacity.py`, `tests/test_core0_envelope_splice_admission.py`, `tests/test_core0_response_admission.py`; updated `tests/test_mqtt.py`, `tests/test_config_manager.py`, `tests/test_core1_startup_heartbeat.py`, `tests/test_memory_error_propagation.py`.

- **Unreleased** (firmware 0.4.45): **Hot-reload integration across Core 0 and Core 1.** A `HOT_RELOADED` `write-config` is now one explicit transaction across both cores over a dedicated inter-core **config-update lane** (request/result), replacing the prior event-queue re-grid. The atomic runtime rule holds: the full candidate becomes the active snapshot or the transaction is rolled back; a mixed candidate (any reboot-required delta) is `REBOOT_REQUIRED` and applies nothing on either core.
  - **`intercore.py`** gains `ConfigUpdateLane` — a narrow latest-value request/result mailbox (`allocate_lock`-guarded, like `state_mailboxes`, no heap admission, no busy-spin on unlocked state) with a monotonic `generation` so a stale result can never be read as the current one. `InterCore` now exposes it as a fourth lane.
  - **Core 0** (`core0.py`) applies its five live HOT settings (a changed `mqtt_command_poll_ms` re-anchors the last-poll stamp to the reload instant so the new cadence starts cleanly), posts one request carrying only the changed Core 1 keys, and holds the response and the file commit until Core 1's acknowledgement is resolved in the run loop: **success** → commit (release the retained `config.json.old`) and send the success response; **failure** → restore the applied Core 0 values, roll the file back, and answer the bounded `error.code` Core 1 posted. The manager's `transaction_active` enforces single-flight; a second `write-config` while one is pending is refused with `config_update_in_progress`. A dead Core 1 never acks, but that is bounded by the existing liveness watchdog (board reset; boot recovery restores the retained `.old`).
  - **Core 1** (`core1.py`) takes the request, **re-anchors** each changed interval from the reload instant (`next = now + interval` — a new scheduling boundary, not re-gridded to the boot anchor; no catch-up sample for a shortened interval), refreshes its own `config` copy so the health activity threshold (which reads `read_loop_sec`) uses the new value, and posts exactly one result — success, or a bounded failure after restoring the prior values (an apply failure leaves Core 1 unchanged). Config-update traffic stays on its own lane and never mixes with the `get-details` user-command event queue.
  - New/updated tests: `tests/test_core1_config_update.py` (re-anchor, config-copy refresh, lane apply/ack, apply-failure rollback), `tests/test_read_write_config_commands.py` (lane ack flow, poll-stamp re-anchor, single-flight refusal, mixed-candidate no-apply), `tests/test_command_protocol.py`, and `tests/test_intercore.py` (the lane). `config_schema_version` (7) and `message_schema_version` (3) unchanged; `FIRMWARE_VERSION` 0.4.44 → 0.4.45.

- **Unreleased** (firmware 0.4.44): **Whole-device configuration validation.** `write-config` and startup now reject a candidate whose complete device definition is structurally/semantically invalid *before* persistence — without touching live hardware — where previously only generic device structure was checked and device-specific rules only ran in a driver's `initialize()`.
  - A **pure device-validation path** is added near `device_factory.py`, which owns the supported `device_type` registry: each registered type maps to a **pure config validator** plus its **allowed config keys**, and the new pure entry point **`validate_device_definition()`** checks the generic device-definition shape, rejects unknown definition fields, verifies the `device_type` is supported, and dispatches to the type's pure validator — it never constructs or initializes a hardware resource (a valid definition with no physical backing passes, leaving physical absence to the boot-time `initialization_failed` outcome).
  - The `system-information` rules move to an authoritative pure validator in **`devices/system_information/validation.py`** (host-importable, no `machine`): `include` must be a non-empty list of unique strings drawn from `SYSTEM_INFORMATION_SECTIONS`, and **unknown config keys are now rejected** (previously not checked). The section constant now lives there; `system_information.py` and the driver read it from there. `SystemInformationDevice.initialize()` calls the same pure validator, so startup and write-time share one rule set.
  - `config.py::validate_config()` (shared by startup `load_config()` and the write-config command) now runs the pure device validation and **aggregates unknown device-config keys** into the sorted `unknown_config_fields` array, qualified `devices[<id>].config.<key>` (definition-level unknowns stay `devices[<id>].<key>`). A new `unsupported_device_type` code answers an unregistered type. `DeviceValidationError` (a `ValueError`, stable `code`) is the pure-validation exception; `config.py` maps it onto `ConfigError`.
  - Change classification (any `devices` delta → `REBOOT_REQUIRED`) and compact whole-device `ADDED`/`REMOVED`/`MODIFIED` reporting were already in place and are unchanged; no live `DeviceManager` mutation occurs from `write-config`, and tolerant startup semantics (independent per-device init, one failure does not invalidate the rest) are unchanged. New/updated tests: `tests/test_device_validation.py`, updated fixtures in `tests/test_config_manager.py` and `tests/test_read_write_config_commands.py`. `config_schema_version` (7) and `message_schema_version` (3) unchanged; `FIRMWARE_VERSION` 0.4.43 → 0.4.44.

- **Unreleased** (firmware 0.4.43): Implemented `read-config`/`write-config` end-to-end with a new Core 0-owned **`config_manager.py`** — configuration persistence, ACTIVE-vs-PERSISTED state, change classification, file transactions, and boot recovery. `config.py` keeps schema validation and per-core splitting as the single source of truth: the pure validation portion of `load_config()` is extracted into **`validate_config(config)`** (no filesystem, no hardware) shared by startup and write-config, and `ConfigError` gains a minimal structured surface (`code`: `unknown_config_fields` / `missing_key` / `invalid_value` / `invalid_config_schema_version` / `unreadable_file`, a sorted `unknown_fields` list covering top-level keys and device-entry keys qualified as `devices[<id>].<key>`, and a flat `details` map such as the expected/received `config_schema_version`) while `str(err)` stays the human-readable message.

`config.json` is the authoritative **PERSISTED** configuration ("what the next reboot will load"); **ACTIVE** is what the running firmware uses. `reboot_required` is **derived** from a compact serialized ACTIVE snapshot (`snapshot exists <=> reboot pending`), never a sticky flag, and a reboot simply clears it — no `needs_reboot` file. The manager retains no duplicate permanent full config dict in the normal state. Classification is an explicit **per-key change-policy table** covering every required config key except the `config_schema_version` invariant (`UNCHANGED` / `HOT_RELOADED` / `REBOOT_REQUIRED`; HOT: `read_loop_sec`, `health_interval_sec`, `datetime_sync_interval_min`, `network_snapshot_interval_sec`, `network_probe_timeout_sec`, `mqtt_command_poll_ms`, `mqtt_outbound_publish_delay_ms`; everything else REBOOT) — a future key without a policy fails the coverage test rather than defaulting silently.

File roles: `config.json` committed; `config.json.tmp` fully-written uncommitted candidate; `config.json.old` previous committed config retained only during a HOT transaction. The write path is: validate → classify → (first reboot transition: serialize the ACTIVE snapshot **before** any file change) → write `.tmp` → `os.sync()` → **read back and re-validate** → rename `.json`→`.old` → `.tmp`→`.json` → `os.sync()`; REBOOT deletes `.old` and commits, HOT keeps `.old` until runtime application succeeds (**commit**) or fails (**rollback**, restoring the previous committed config and the pre-transaction reboot state). **Boot recovery** runs before startup and settles artifacts in priority order: valid `config.json` wins (stale `.old`/`.tmp` cleaned only after the decision) → valid `.old` restored → valid `.tmp` promoted → otherwise `ConfigError`; steady state after any success is exactly one valid `config.json`.

Commands: **`read-config`** (payload exactly `{}`) answers `data: {config, reboot_required}` with the committed configuration (Wi-Fi secrets never cross). **`write-config`**'s payload is exactly `{"config": <complete candidate configuration>}` — unknown payload keys are named together in a sorted `unknown_fields` array, and there is no patch/merge/partial-update shape — validated by the same `validate_config()` startup uses (a schema-version mismatch fails the operation with `invalid_config_schema_version` naming `expected`/`received`; unknown configuration fields — top-level or device-entry qualified — are returned together as `unknown_config_fields`); the success answer carries `data: {configuration_changed, classification, reboot_required, changes}` where `changes` is a deterministic summary of PERSISTED-before vs candidate (scalar `original_value`/`new_value` pairs; compact whole-device `ADDED`/`REMOVED`/`MODIFIED` entries with `device_id`/`device_type`, or one bounded list-level `MODIFIED` entry for a difference no id accounts for). A `*` write-config is silently ignored (no validation, no write, no response); write-config never reboots by itself, and a `REBOOT_REQUIRED` answer is still published on the currently active source/MQTT session. **HOT_RELOADED** writes are applied before committing: Core 0 updates its five live HOT settings in place (`mqtt_command_poll_ms` is now read per run-loop pass), and Core 1 receives one **internal config-update event** (`read_loop_sec`/`health_interval_sec`) that re-grids its read/health schedulers from the unchanged normal-runtime anchor (missed boundaries skipped, never replayed); a Core 1 admission failure restores the applied Core 0 values and rolls the file transaction back (`intercore_event_queue_memory_pressure`). `MemoryError` keeps the firmware's fail-fast recovery policy. `main.py` now boots through `ConfigManager.recover()`; `core0.py` takes the manager (never shared with Core 1). New/updated tests: `tests/test_config_manager.py`, `tests/test_read_write_config_commands.py`, `tests/test_core1_config_update.py`, extended `tests/test_config.py`, updated protocol/recovery/scheduler-anchor expectations. `config_schema_version` (7) and `message_schema_version` (3) unchanged; `FIRMWARE_VERSION` 0.4.42 → 0.4.43.

- **Unreleased** (firmware 0.4.42): Established one strict, predictable command protocol boundary before command execution. A new `command_protocol.py` module holds the protocol constants and pure validation helpers (command names, envelope keys, string bounds, ownership sets, broadcast policy) — no classes, no framework — and `core0.py` now validates every command in a fixed staged order: decode → dictionary → **global `message_schema_version` gate** → command topic → `message_type` → bounded target match → bounded `command_id` → debounce (claim) → envelope unknown fields → required fields/types → bounded command name → registry → broadcast policy → command-specific dispatch.

The **global inbound message-schema gate** applies to every decoded inbound MQTT object, not only commands: a missing, wrong-typed, older, or newer `message_schema_version` is ignored for the whole message — no response, no debounce-cache entry, no UTC/request state change, no topic-specific processing — including inbound `info_response`. The firmware does not attempt to interpret a wire protocol version it does not support, so the previous `invalid_message_schema_version` command response is removed.

The **supported-command registry** now names all four protocol commands and their owners: `reboot` (Core 0-owned, executed on Core 0; `machine.reset()` is Core 0's), `get-details` (Core 1-owned, dispatched as a validated bounded event — the authoritative `SystemInformation` instance and device state live on Core 1), `read-config` and `write-config` (Core 0 / configuration manager). A command name outside the registry is **unknown** and is answered by Core 0 with `error.code: "unsupported_command"` (`"Unsupported command"`) preserving the actual name in the standard `payload.command` field — never routed to Core 1, which no longer acts as the generic fallback for arbitrary command names (its `unsupported_command` fallback and `payload != {}` re-check are removed; it keeps the `system_information_unavailable` failure and the full-snapshot response). `read-config`/`write-config` are **recognized** (not `unsupported_command`) but their payload contracts belong to the configuration specification, which is not in this firmware yet: a validated request for them is answered with a bounded `error.code: "not_implemented"` stating the actual cause.

The **broadcast policy** is per-command: `*` is valid for `reboot`, `get-details`, and `read-config`, but a recognized `write-config` for `*` is silently ignored — no configuration validation, no filesystem operation, no response (its claimed ID remains in the debounce cache). Target matching is case-insensitive for both the configured `source` and the device's current IP address (same case-insensitive string comparison), with the configured casing preserved in stored values and emitted messages.

**String bounds** are enforced at the protocol boundary (independent of the per-message MQTT size ceiling): `command_id` ≤ 128 characters, `command` ≤ 32, `target` ≤ 128, all non-empty when required. An over-long `command` is answered with a bounded `error.code: "invalid_command"` and is **never echoed into the response** (not even partially) — a command response carries the `command` field only while it is bounded and valid, so a single command can never build an oversized error substitute and stall the channel. A missing/non-string/empty/over-long `command_id` is dropped silently (a standard response requires a bounded `command_id`) and is never cached; an over-long target simply does not match. Unknown command-envelope top-level fields violate the v3 contract: all of them at that scope are named in one **sorted** `unknown_fields` array (`"Message contains unknown fields"`).

The **command-ID debounce cache** semantics are fixed: capacity 16, FIFO eviction, exact/case-sensitive comparison, RAM-only (reboot clears it; never persisted), a duplicate does not refresh its FIFO position, and a duplicate is silently ignored. The first **bounded** targeted ID is claimed **before deeper validation** — a malformed command still claims its ID, so repeated copies of the same malformed message cannot generate repeated validation responses (first response owed, duplicates suppressed). Never claimed: gate failures, another device's traffic, and unbounded `command_id`s. The shared `{}`-only payload contract for `reboot`/`get-details` (any key is an unknown field, named sorted; missing/non-object payload is `invalid_payload`) and the `get-details` bounded-event dispatch (`{command_id, command, payload: {}, targeted}`, `intercore_event_queue_memory_pressure` on admission failure) are preserved, as is the `reboot` behavior (single pending, `reboot_already_pending`, success acknowledgement published before `machine.reset()`). `tests/test_command_protocol.py` (new) pins the global gate (command and `info_response` paths, no response/no cache/no UTC state change), the per-command broadcast policy, case-insensitive IP targeting, the length boundaries, the envelope `unknown_fields` answer, `invalid_command`/`unsupported_command`/`not_implemented`, and malformed-duplicate suppression; `tests/test_command_id_deduplication.py`, `tests/test_get_details_command.py`, and `tests/test_command_target_matching.py` are updated for the new contract. Retired: the `max_outbound_queue_entries`/`max_intercore_event_entries` config keys (`config_schema_version` 6 — configs carrying them fail fast as unknown keys), the `outbound_queue_capacity`/`outbound_queue_utilization_percent`/`outbound_max_queued_bytes`/`outbound_queue_byte_utilization_percent` health fields, the `outbound_queue_pressure` degradation reason (a below-reserve heap is itself the pressure condition, reported as `low_free_heap`), and `split_config()`'s third `bus_config` return value. Added health fields: `outbound_queue_high_watermark`, `outbound_queue_high_watermark_bytes`, `outbound_evicted`, `telemetry_evicted`, `outbound_rejected` (depth and `outbound_queued_bytes` retained); `SystemInformation.get_queues()` exports the same observability view plus the event-queue pending/high-watermark/rejected counters. `OutboundQueue.status()` now reports the depth/bytes high watermarks and eviction/rejection counters in place of the old capacity views; the queue-internal byte accounting (in-flight bytes retained until PUBACK) is unchanged. `MemoryError` propagation semantics are preserved throughout. `config_schema_version` bumped to 6 (no `message_schema_version` change).

- **0.4.25**: Made command target matching case-insensitive. `Core0._target_matches()` compared the command `target` against the configured `source` with exact string equality, so a logically equivalent casing variant (e.g. `teSt-PICO-2` for a device configured as `Test-Pico-2`) silently failed to match and the command was ignored with no response. The source comparison now normalizes both sides with `lower()` (MicroPython-safe, no `casefold()` dependency) at the comparison boundary only: the stored/configured source keeps its original casing, responses are still emitted with the configured casing via `_envelope_fragment()`, and the broadcast (`*`) and IP-address targeting paths are unchanged. A non-string `target` still simply fails to match (an `isinstance` guard preserves that without raising where `lower()` would). Applies to every command on the shared routing path; no command-specific logic. Behavior fix (no `config_schema_version` or `message_schema_version` change).

- **0.4.24**: Added the Core 1 `get-details` command. The command requires an empty payload and returns a current full system-information snapshot directly in `command_response.payload.data`, collecting every section named by `SYSTEM_INFORMATION_SECTIONS` regardless of the configured `system-information` telemetry device `include` list. The implementation reuses the existing full-system-information collector used by the startup log, preserving one source of truth for section collection and the existing per-section error behavior. Additive command behavior only; no config or message schema version change.

- **0.4.22**: Made the 16 KiB per-message ceiling a queue invariant on both admission paths, not just a property of the `put()` serialization path. `put()` enforces it via `serialize_and_validate_message()` (a `MessageTooLargeError` rejection), but `put_with_kind()` — the pre-serialized-bytes path both production callers (startup log, health message) use — passed bytes straight to `_admit_locked()` with no per-message size check: the 32 KiB aggregate byte budget therefore admitted a single entry of up to 32 KiB through that path, invalidating the 16 KiB transient-peak rationale (graph + str + bytes ≈ 3x the payload ≈ 48 KiB) both memory bounds are sized against. Both shipping callers serialize first and were safe, so this closed an invariant gap (two sources of truth for the memory rule) rather than a live defect. `put_with_kind()` now rejects any payload longer than `MAX_OUTBOUND_MESSAGE_BYTES` — the same constant `put()` enforces — incrementing the existing `oversized_rejected` counter and leaving queue state untouched, exactly like the `put()` path. No re-parsing or JSON allocation (a length check on final bytes), and the caller contract (bytes are already validated, serialized JSON) is unchanged. Failure-path behavior change (no `config_schema_version` change).

- **0.4.21**: Made the outbound byte budget account for the in-flight entry's retained bytes, so the budget now caps ALL payload bytes the outbound queue retains, not just the queued FIFO. The in-flight entry is popped out of the FIFO by `take()` and held until its PUBACK (`complete_in_flight`), so its payload bytes stay resident the whole time — but `take()` subtracted them from the byte count the moment the entry moved in-flight and `complete_in_flight()` never re-added them. The budget therefore capped only the queued FIFO: a 16 KiB in-flight payload plus a full 32 KiB of queued payloads could be resident at once (48 KiB) while `outbound_queued_bytes` reported only 32 KiB, and admission kept granting the full 32 KiB of queued room on top of whatever was in flight. Now `take()` leaves the entry's bytes counted, `complete_in_flight()` releases exactly the completed entry's bytes, and eviction subtracts queued entries as before — the in-flight payload consumes budget for as long as it is retained. This tightens the worst-case retained payload from 48 KiB to 32 KiB and makes the two budget views consistent: `outbound_queue_depth` already included the in-flight entry, and `outbound_queued_bytes` now does too. `outbound_queued_bytes` (health and startup log) can now read slightly higher while an entry is in flight; `outbound_max_queued_bytes` is unchanged. Steady-state memory-boundary change (no `config_schema_version` change).

- **0.4.20**: Made a Core 0 command/reboot response retry the same wire document, not just the same sequence identity. 0.4.17 made `(runtime_id, sequence)` a reliable unique event identity by claiming the sequence before the first transmission attempt and stamping it on the logical object so a retry reuses it — but for Core 0's own retryable responses (the pending command responses and the pending reboot) the identity was preserved while the *content* was not: `_publish_core0_command_response()` rebuilt the message (re-capturing `uptime_ms` and `timestamp`) and re-serialized it on every attempt, so an ambiguous QoS 1 failure (the PUBLISH reached the broker but the PUBACK was lost) followed by a retry put two packets with the *same* `(runtime_id, sequence)` on the wire carrying *different* documents (differing `uptime_ms`/`timestamp`). A downstream deduplicator keyed on that identity could then discard one of two differing documents depending on arrival order. Queued telemetry never had this problem because its pre-serialized bytes stay attached to the same in-flight queue entry. The serialized bytes are now frozen on the persistent logical object on the first attempt (a new `container` parameter on `_publish_core0_command_response()`, the pending response dict or the pending reboot dict, mirroring the queue's in-flight entry) and re-published verbatim on a retry, so a retry is the same logical message with the same identity AND the same content. The wire format and the QoS 1 at-least-once guarantee are unchanged; only the pathological ambiguous-failure-then-retry case now emits byte-identical frames. Failure-path behavior change (no `config_schema_version` change).

- **0.4.19**: Made the disposal of a failed MQTT client bounded too, closing the last unbounded write on Core 0's network path. 0.4.16 bounded the QoS 1 PUBLISH frame writes and the PUBACK wait, but the cleanup of the client left behind after such a failure was not: `Mqtt._close_old_client()` — the first step of every `connect()` attempt, i.e. of every reconnect — called `MQTTClient.disconnect()`, which unconditionally wrote an MQTT DISCONNECT frame. After a failed bounded exchange, the exchange's `finally` had already restored the socket to infinite-blocking mode, so that DISCONNECT write into the already-failed link had no deadline: on a blackholed link (TCP up, sends not draining) it wedged Core 0 inside `sock.write()` forever, and with Core 0 wedged its Core 1 heartbeat watchdog (0.4.9) could never run either — the same P1 class 0.4.16 fixed for the PUBLISH itself, one step later in the failure chain (publish stalls → bounded timeout → socket restored to infinite blocking → reconnect → unbounded DISCONNECT write → permanent wedge). Disposal now closes the TCP socket directly with no write at all: this path only ever runs while the session is not connected (`connect()` is only entered from `establish_network()`'s `while not is_connected()`), so the old client is always failed or never established and no graceful DISCONNECT frame is needed — the broker drops the clean session when the TCP connection closes. Failure-path behavior change (no `config_schema_version` change).

- **0.4.18**: Made the queued-byte budget visible to system telemetry and health, so the queue's memory-protection boundary can no longer be full while health reports no pressure. The byte budget (0.4.8: 32 KiB of queued payload bytes, enforced alongside the 16-entry count) was only ever reported as entry counts: `SystemInformation.get_queues()` (the startup-log source) and the health payload both carried no byte view, and `outbound_queue_pressure` was computed from entry utilization alone — a handful of large entries (e.g. 4 × ~8 KiB) could sit at 25% entry utilization while the byte ceiling was at 100%, the exact condition the budget exists to flag. The health payload now carries `outbound_queued_bytes`, `outbound_max_queued_bytes`, and `outbound_queue_byte_utilization_percent` (sourced from a new single-lock `OutboundQueue.get_health_metrics()` reading both budget views consistently), `SystemInformation.get_queues()` now exports the two byte fields, and `outbound_queue_pressure` fires at `max(entry_utilization, byte_utilization) >= 75%`. Queued bytes exclude the in-flight entry, matching the byte admission budget in `_admit_locked`; the entry-depth field still counts it, as before. The byte-utilization computation is integer-only (MCU-safe), no new config or schema surface. Additive wire change (three new health payload fields); no `config_schema_version` change.

- **0.4.17**: Made the wire `sequence` reliable across an ambiguous QoS 1 failure. The sequence was consumed only after a successful PUBACK, so in the ambiguous case — the PUBLISH reached the broker but the PUBACK was lost — the number was never consumed and was handed out again: a `mqtt_connection_established` log published after the reconnect took the in-flight telemetry's sequence (a `(runtime_id, sequence)` collision on the wire), and the telemetry retry then took a still-newer one, so the same logical sample appeared under two identities and an unrelated message reused the sample's number. The sequence is now claimed before the first transmission attempt and stamped on the logical object — the queue entry, or Core 0's persistent response/reboot dict for its own retryable messages (`_claim_wire_sequence` in `core0.py`) — and is never rolled back: a retry of the *same* logical message reuses the stamped number (both copies identify one message, legitimate QoS 1 duplicate delivery), while a *different* message always gets a fresh number. `(runtime_id, sequence)` is therefore now a safe unique event identity and a retry is recognizable as the same message. The wire format is unchanged (same top-level keys, same Core 0 values) and the QoS 1 at-least-once delivery guarantee is unchanged. Failure-path behavior change (no `config_schema_version` change).

- **0.4.16**: Bounded the QoS 1 PUBLISH frame writes, not just the PUBACK wait. `MQTTClient.publish()` installed the socket timeout only *after* all four socket writes (header, topic, packet id, payload), so a link failure that leaves TCP apparently established while sends stop making progress wedged Core 0 inside `sock.write()` — and with Core 0 wedged, its Core 1 heartbeat check (the 0.4.9 watchdog) never ran, leaving no recovery path. The timeout is now installed before byte 1 of the frame and restored only after the exchange finishes, so the frame writes and the PUBACK wait share one bounded deadline: a stalled write surfaces as a bounded error into `Mqtt.publish_qos1`'s disconnect + network recovery (the entry stays in flight, at-least-once semantics unchanged). Wire order (header, topic, packet id, payload) and the QoS 0 path are unchanged; a failed timeout installation now aborts before any byte is transmitted instead of after the full frame. Failure-path behavior change (no `config_schema_version` change).

- **0.4.15**: Made `MemoryError` propagation consistent on the Core 0/Core 1 message paths. Heap exhaustion is a fatal condition, not a failed optional diagnostic, but several allocation-heavy paths swallowed it in a generic `except Exception` handler and kept the core running on top of an exhausted heap: `core1._collect_system_information_full()` (a failed section was recorded as `{"error": ...}`), `core1._try_queue_startup_log()` and `core1._try_queue_health_message()` (the message was silently discarded as if serialization had merely failed), `core1._build_health_payload()` (heap/hardware fallbacks), the Core 1 startup hardware storage, `core0._service_pending_connection_log()`, and `core0._publish_core0_command_response()` (whose handler was `except (MessageTooLargeError, Exception)` — effectively `except Exception`). Every one of these now re-raises `MemoryError` before the generic handler, matching the convention every other module already followed. Heap exhaustion now stops the core with a diagnosable error instead of obscuring the root cause or making fragmentation worse, and the callers' existing `except MemoryError: raise` clauses (e.g. `_perform_reboot`) can now actually fire. Ordinary (non-`MemoryError`) failures are still handled as before: reported and the message discarded. Failure-path behavior change only (no `config_schema_version` change).

- **0.4.14**: Stopped the telemetry scheduler from replaying missed boundaries as catch-up reads. When a device read stalled long enough to cross one or more `read_loop_sec` boundaries, the deadline advanced by a single interval per pass, so the loop fired an extra read almost immediately — and another, until it caught up: a burst of near-identical current samples, JSON work, and queue admissions landing right after the overload. Telemetry is a current sample, not a replayable record, so a stall cannot reconstruct the missed samples; the scheduler now performs the current sample once and skips directly to the next future boundary — the same missed-boundary policy the health scheduler already used. The skip is evaluated against a clock re-read after the read completes, because the loop's captured clock is stale by however long the read took and would otherwise under-advance and leave a catch-up read for the next pass. Outage buffering is unchanged (an MQTT outage still queues telemetry rather than dropping it); this only changes the pathological slow-read case. Static behavior change (no `config_schema_version` change).

- **0.4.13**: Eliminated the double serialization on the publish path. A queued message was serialized by its sender and then, on Core 0, decoded, parsed back into a dict, merged with Core 0's envelope fields, and re-serialized as a whole document (`dict → str → bytes → queue → str → dict → str → MQTT`): the message body was serialized twice, and the transient allocations, CPU, and fragmentation risk accumulated exactly where the queue was supposed to improve memory predictability. The contract is now: the sender carries its complete message — including `uptime_ms` and `timestamp` (null when UTC is unsynchronized) — and must not carry any envelope key at the top level (`sequence`, `runtime_id`, `source`, `firmware_version`, `message_schema_version`); Core 0 injects those five members at publish time by splicing them into the stored serialized object before its closing brace. The payload is never decoded, parsed, or re-serialized on the publish path, so publishing allocates only the small envelope fragment plus the assembled frame. The wire format is unchanged (same top-level keys, same Core 0 values) and the queue still stores immutable pre-serialized bytes — the frame is a fresh allocation, the entry is untouched. Core 1 no longer pre-embeds `runtime_id`/`source`/`firmware_version`/`message_schema_version` (they were always overwritten by Core 0 anyway), and the health/startup-log `timestamp` is computed from the shared UTC snapshot instead of being left null for Core 0 to fill (which required the parse it could no longer afford). Static behavior change (no `config_schema_version` change).

- **0.4.12**: Bounded the inbound MQTT packet size. `wait_msg()` now rejects a PUBLISH whose remaining length exceeds `MAX_INBOUND_PACKET_BYTES` (16 KiB — the same MCU-scale ceiling as the outbound limit) *before* allocating its payload: previously `sock.read(sz)` was handed whatever the broker's remaining-length field claimed, and a broker-side bug publishing an oversized command/info response could request an allocation large enough to exhaust the Pico W's RAM (no hostile traffic required). An oversized frame — like a fifth remaining-length byte (an MQTT protocol violation that was previously an unbounded read loop) — now closes the socket and raises `MQTTException`, which the `Mqtt` layer turns into a marked disconnect and Core 0's existing recovery path reconnects, instead of trying to buffer or drain the corrupt stream. Static constant (no `config_schema_version` change).

- **0.4.11**: Fixed the MQTT receive path parsing incoming packets in non-blocking socket mode. `check_msg()` now decides *readiness* with a non-blocking `select` poll — one readable byte means a packet has started; nothing returns `None` immediately and leaves the socket mode untouched — and only then parses the packet on a blocking-with-finite-timeout socket bounded by `mqtt_broker_response_timeout_sec`. Previously the whole multi-byte parse ran non-blocking, and because MicroPython documents that `read(n)` may return fewer bytes than requested in non-blocking mode, a PUBLISH split across TCP reads could short-read its topic or payload and deliver a corrupt frame (or raise a spurious disconnect) instead of waiting for the rest of the packet. Now a link that stalls after the first frame byte surfaces as a bounded timeout into the existing recovery path, and a ready packet is always fully read. `wait_msg()` and the bounded-wait invariants are otherwise unchanged; `check_msg()` now installs and restores its own finite timeout like `publish`/`ping`. Static behavior change (no `config_schema_version` change).

- **0.4.10**: Made startup verification self-healing to match the (already) unbounded connect loops. Previously the QoS 1 probes and UTC sync were the only fail-fast steps: a single transient blip after connection — a dropped PUBACK on a probe, or a brief UTC-server outage across the 3 bounded attempts — raised `RuntimeError` out of `core0.start()`, exited `main()`, and left the device stopped until a physical reset, even though a broker that was *never* reachable would have looped forever. `start()` now keeps the verification steps (probe #1 → drain → 5 s wait → probe #2 → UTC) in a new `_verify_startup_contract()` pass inside a retry loop: on any pass failure it drops the MQTT session (`mark_disconnected()`), re-establishes the network, and retries the whole pass, reusing the existing `mqtt_reconnect_delays_sec` backoff. Core 1 stays gated because `start()` has not returned and `_network_stack_ready` is set only after a clean pass; a `MemoryError` still propagates (fail-fast) so an out-of-memory device is not looped. Static behavior change (no `config_schema_version` change).

- **0.4.9**: Core 0 became the independent consumer of the Core 1 liveness heartbeat, closing the P1 failure mode where a dead or wedged Core 1 thread (an unhandled `MemoryError`/`Exception`) wedged the whole sensor — telemetry and health silently stopped, a dead Core 1 could not build the health message that would report `core_1_inactive`, and Core 0 kept running indefinitely with no recovery. The Core 0 run loop now checks `core_1_activity_ms` first on every pass (`_watch_core_1_heartbeat` in `core0.py`): before any stamp exists (Core 1 has not started) the check is a no-op, so the unbounded startup connect loops are unaffected; once a stamp exists, age at or beyond `_CORE_1_HEARTBEAT_STALE_TIMEOUT_MS` (30 s — more than six missed 5 s refreshes, and below the 60 s `core_1_inactive` diagnostic threshold) logs FATAL and calls `machine.reset()`. Static constant (no `config_schema_version` change).

- **0.4.8**: Made the outbound message/queue limits MCU-safe. The per-message ceiling dropped from 128 KiB to 16 KiB (`message_serializer.MAX_OUTBOUND_MESSAGE_BYTES`) — the check runs after `json.dumps()` + UTF-8 encode, so the object graph, serialized `str`, and encoded `bytes` are all resident at once and a 128 KiB payload could not be admitted safely on a Pico W; 16 KiB bounds a single message's transient peak (~48 KiB) with margin over the largest legitimate message (the startup log). `OutboundQueue` is now bounded by BOTH entry count and an aggregate queued-byte budget (`DEFAULT_MAX_OUTBOUND_QUEUED_BYTES` = 32 KiB), so 16 retained payloads can no longer exhaust heap on their own; admission enforces both budgets and only evicts when it frees enough room (by count or bytes), never dropping a valid entry to admit one that would not fit. Both bounds are static constants (no `config_schema_version` change); `OutboundQueue.status()` now also reports `queued_bytes` and `max_queued_bytes`.

- **0.4.7**: Fixed the MQTT handshake blocking indefinitely: `Mqtt.connect()` now passes `mqtt_broker_response_timeout_sec` to `MQTTClient.connect()`, bounding the CONNACK wait — and, since `subscribe()` inherits that socket timeout, both SUBACK waits. A broker that accepts the TCP connection and then stops responding now fails the connect attempt (retried with the reconnect backoff) instead of wedging Core 0 forever; the socket returns to normal blocking mode once both subscriptions succeed.

- **0.4.6**: One shared normal-runtime scheduling epoch for all periodic Core 1 work. `normal_runtime_start_ticks_ms` is captured exactly once, immediately after `system_startup_completed` is admitted to the outbound queue; both the telemetry deadline (`anchor + n × read_loop_sec`) and the health deadline (`anchor + n × health_interval_sec`) derive their fixed boundaries from that anchor. Telemetry and health remain independent schedulers (shared epoch, no execution dependency); neither deadline derives from the other. `boot_ticks_ms` remains the boot-lifetime reference for uptime (`uptime_ms`) and startup-duration measurement only. Reconnects, UTC resyncs, and device reinitialization never reset the anchor; only a reboot creates a new one. Health outage policy is unchanged (missed intervals skipped, never replayed); telemetry outage buffering is unchanged.

The immediate post-startup health message is removed; boundaries missed during startup or an MQTT outage are skipped, never replayed; deadlines advance from the previous boundary so processing delay cannot accumulate drift.
