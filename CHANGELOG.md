# Changelog

This document records notable changes to the project across released versions.

Changes are organized by version in reverse chronological order, with the most recent release listed first. Each version should summarize meaningful changes such as new features, fixes, behavioral changes, refactoring, configuration changes, and other updates relevant to developers or operators.

## Versioning

Project versions follow Semantic Versioning where practical:

- **MAJOR** — incompatible or breaking changes
- **MINOR** — backward-compatible features or significant enhancements
- **PATCH** — backward-compatible fixes, maintenance, and small improvements

## Change Categories

When applicable, changes should be grouped under clear categories such as:

- **Added**
- **Changed**
- **Fixed**
- **Removed**
- **Deprecated**
- **Security**

## Version History

- **Unreleased** (firmware 0.4.41): Stopped the startup connection-log drain from timing out the later logs because of an earlier log's slowness. `_drain_startup_mqtt_work()` measured one shared 2 s budget from the drain's start across all pending connection logs, but each log's cycle legitimately includes a blocking QoS 1 PUBACK wait the system allows up to `mqtt_broker_response_timeout_sec` (4 s) — so the drain's budget was shorter than a single legal cycle, and one slow-but-legal cycle (e.g. the first post-connect exchanges on a hotspot link) consumed the budget of every log behind it, deferring them to the Core 0 run loop with two `[WARNING]` lines. Each pending log is now measured against its own 2 s grace window starting when the previous log's cycle completed, so a slow cycle can no longer eat the next log's budget; the drain stays bounded (each window plus the per-publish PUBACK cap) and non-fatal, and the run-loop backstop for any leftover log is unchanged. `tests/test_outbound_publish_pacing.py` adds a regression test pinning that a 3 s first-log cycle still lets the second log drain within its own window (the old shared budget deferred it). No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.40 → 0.4.41.

- **Unreleased** (firmware 0.4.41): Emit an initial telemetry sample and an initial health report at boot. After `system_startup_completed` is admitted, Core 1 now runs one telemetry read pass and one health report immediately (telemetry first, so the health report reflects queue state that already includes the fresh samples), before the periodic schedulers begin — a subscriber that connects at boot no longer waits a full `read_loop_sec` (20 s) for the first telemetry or a full `health_interval_sec` (60 s) for the first health. The initial pass reuses the existing periodic read path (factored into `_run_telemetry_read_pass()`) and the existing network-gated health path (`_try_queue_health_message_intercore()` — still skipped when the network snapshot says not ready), so admission, retention, and the permanent-rejection policies are unchanged. The shared normal-runtime anchor and both periodic deadline initializations (`anchor + n × interval`) are untouched: the initial sample is a one-shot at the anchor moment, not a second grid, and cannot accumulate drift. `tests/test_health_scheduling.py` and `tests/test_scheduler_anchor.py` are updated for the inverted contract (the "no immediate health" tests now assert exactly one immediate report at the anchor, queued after the startup log, with the first periodic boundary unchanged). No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.40 → 0.4.41.

- **Unreleased** (firmware 0.4.39 → 0.4.40): Reduced the module, class, and function docstrings across the firmware and test suite — removing verbose multi-paragraph prose and redundant `Args:`/`Returns:`/`Raises:` blocks, and condensing the rest to the one or two sentences that still carry the contract (e.g. the transient-vs-permanent admission distinction, the never-rolled-back wire sequence claim, the startup-only publish-slot wait). A net 1,211 lines (about 34 KiB) of source shrink, which on a 256 KB device is flash and parse time saved at every boot, with no executable change: the diff touches docstring text only. All 344 host tests pass unchanged. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.39 → 0.4.40.

- **Unreleased** (firmware 0.4.38 → 0.4.39): Stopped the Core 1 command response channel from misreporting what permanently rejected a response. `OutboundQueue.put()` and `put_with_kind()` collapsed every permanent rejection into a generic `ValueError`, so `core1.py`'s `_admit_or_substitute_command_response()` — which must answer a permanently rejected response with a small substitute for the same command instead of stalling the channel behind it — substituted `error.code: "response_too_large"` for every cause: a serialization/validation bug in the response was reported to the command sender as a size problem, obscuring the real firmware defect. The size case now carries its own type through the queue boundary: both admission paths raise a new `OutboundMessageTooLargeError` (a `ValueError` subclass, so every existing permanent-rejection handler — telemetry and health discard, startup-log fail-fast — keeps working unchanged) only when the serialized payload exceeds `MAX_OUTBOUND_MESSAGE_BYTES`, while a validation or serialization failure still raises a plain `ValueError`. The command channel now answers each cause with the code that states it: an oversized response still gets the small `response_too_large` substitute, while a validation or serialization failure gets `error.code: "response_invalid"` (the actual error is logged to the console). `_build_response_too_large()` generalizes to `_build_substitute_error_response()` (code and message parameters) and the log/substitute/admit step is factored into `_admit_substitute()`; the transient-rejection contract (False → the same response stays pending for a later pass) and the channel-moves-on guarantee are unchanged. `tests/test_command_response_admission.py` splits the permanent-rejection test into the size case (`response_too_large`) and the validation-failure case (`response_invalid`, verified against the pre-fix code that mislabeled it) and adds a real-queue boundary test pinning the exception type on both admission paths — including that a validation failure is a `ValueError` that is *not* an `OutboundMessageTooLargeError`. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.38 → 0.4.39.

- **Unreleased** (firmware 0.4.37 → 0.4.38): Made the restoration of normal socket blocking mode a connection failure instead of a best-effort, logged-and-ignored step. The socket-mode contract is that `wait_msg()` reads in whatever mode it finds and every caller bounds its own wait — so a socket left out of blocking mode silently defeats the next bounded wait. Yet when the finite exchange timeout was unwound, the three restore sites swallowed non-`MemoryError` failures: `Mqtt.connect()` after the CONNACK/SUBACK handshake (logging the error and still marking the link connected), and the `finally` blocks of `MQTTClient.ping()` and `MQTTClient.publish()` (letting the operation report success). In contrast `check_msg()` already let its restoration propagate. Now all three sites let a failed `settimeout(None)` propagate: a failed handshake restore fails the attempt (the existing reconnect backoff retries and the broken client is closed by the attempt cleanup), a failed ping/publish restore fails that operation into Core 0's existing recovery path, and a `MemoryError` still reaches the final recovery boundary as before. The behavioral change is only in the failure mode that used to be swallowed — the success path and the install-side failure handling (which already propagated) are untouched. `tests/test_mqtt.py` gains a `restore_error` hook on the mock socket (installs still succeed; only `settimeout(None)` raises) and pins the three cases: a ping whose PINGRESP arrived but whose restore fails still raises, a QoS 1 publish whose PUBACK arrived but whose restore fails still raises, and a complete handshake whose blocking-mode restore fails returns `connect() is False` with no connect count and the client's socket closed. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.37 → 0.4.38.

- **Unreleased** (firmware 0.4.36 → 0.4.37): Made Wi-Fi stop waiting out a failed association. `Wifi.connect()` observed every attempt for the full 20-second window (200 × 100 ms) regardless of what the radio was doing, because it only checked `isconnected()` — so a wrong password, a missing AP, or a known connect failure (the driver's terminal association states `WRONG_PASSWORD`, `NO_AP_FOUND`, `CONNECT_FAIL`) still consumed the whole window before the next retry, adding minutes of useless waiting across attempts during failure recovery. The 100 ms wait loop now also inspects the radio's association status (the no-arg `status()` call) after servicing Core 0 on each slice and ends the attempt immediately once it is a terminal failure state, falling straight through to the existing backoff and next attempt. A still-connecting state is not terminal, so the loop keeps observing and the original 20-second timeout remains the fallback for a link that simply never settles; the retry sequence, the 100 ms Core 0 servicing (the Core 1 heartbeat watchdog), and the timeout are all unchanged. The terminal status values are read from the WLAN object (the same way `PM_NONE` is) and, if a firmware build does not expose the `STAT_*` names, fall back to the documented MicroPython values (2, 3, 4); any inability to read the status is treated as unknown and degrades to the existing timeout behavior, so nothing that worked before regresses, and a `MemoryError` still propagates to the final recovery boundary. `tests/test_network_wait_service.py` pins the four cases (a wrong password and a missing AP each bail early with backoff-only elapsed time, a still-connecting state waits the full window, and the documented-value fallback still bails early). No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.36 → 0.4.37.

- **Unreleased** (firmware version unchanged): Fixed the two Pico deployment scripts (`_deploy-to-device-1.sh`, `_deploy-to-device-2.sh`) silently enumerating zero root-level application files. Their `release.py` enumeration referenced `OPTIONAL_FILES`, which the 0.4.36 change that moved `config.json` into `REQUIRED_FILES` removed — the Python `AttributeError` was swallowed inside the Bash process substitution (`mapfile` received empty input even under `set -Eeuo pipefail`), `ROOT_FILES` came out empty, and the "has deployable files" check still passed on the strength of `REQUIRED_PACKAGES`, so a deployment erased the Pico's entire flash and copied only `config.json`, `config-secrets.json`, and the `devices/` package — leaving a working board without `main.py`, `core0.py`, `core1.py`, or any other root module. The enumeration now reads `REQUIRED_FILES` only (restoring all 18 root-level `.py` files), and a new fail-fast staging assertion runs before any flash erase: it verifies the staged tree holds every required root-level file, and independently of the enumeration verifies `main.py` is present, so an empty or broken enumeration can no longer drive a destructive deployment. Build tooling only; no firmware behavior, `config_schema_version`, or `message_schema_version` change; `FIRMWARE_VERSION` unchanged.

- **Unreleased** (firmware 0.4.35 → 0.4.36): Made outbound-message validation allocation-light on the common (valid) path. `serialize_and_validate_message()` eagerly built a per-node diagnostic path string (`root['key'][1]`, …) for every node of every message, including messages that passed validation and never used one — short-lived allocations and fragmentation on the hot path every outbound message pays. It now runs the allocation-light `is_json_safe()` pass first (same rules, no per-node path strings) and only on failure walks the message through the detailed path-producing validator, so a valid message never touches `_validate_value()` at all and an invalid one still raises the same precise error with the offending path (`UnsupportedValueError`, `NonStringKeyError`, `NonFiniteFloatError`) the callers already report. The two passes must accept and reject exactly the same values, and the new `tests/test_message_serializer.py` pins that agreement (plus the nested path diagnostics), so a future drift cannot let an invalid value reach `json.dumps` or misreport a valid message. Float finiteness now uses `math.isfinite()` — consistent with `message_protocol.is_json_safe()` — instead of comparing against fresh `float("inf")` values (two float allocations per float value). No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.35 → 0.4.36.

- **Unreleased** (firmware 0.4.35 → 0.4.36): Hardened the inbound MQTT PUBLISH parser against internally inconsistent frames. The 0.4.12 cap bounds the packet's *remaining length*, but the topic length (and, for a QoS 1 PUBLISH, the packet identifier) is a second size declaration made by the packet itself, and `wait_msg()` trusted it: a corrupt stream could declare a 65535-byte topic while only a few bytes remained, and `sock.read(topic_len)` would request a ~64 KiB allocation on a 256 KB device (and drive the remaining counter negative into subsequent reads). The declared lengths are now validated against the bytes actually remaining *before* each read — a topic length exceeding the remainder, or a frame too short even for the 2-byte topic field (or the packet-ID field) — is treated exactly like an oversized frame: `_abort_corrupt_inbound()` closes the socket before any payload is allocated, raises `MQTTException`, the `Mqtt` layer marks the disconnect, and Core 0's existing recovery path reconnects instead of buffering or draining the corrupt stream. `tests/test_mqtt.py` pins the three new rejection cases (topic length beyond the remainder, a frame shorter than the topic field, and a QoS 1 frame shorter than the packet-ID field). No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.35 → 0.4.36.

- **Unreleased** (firmware 0.4.35 → 0.4.36): Made `config.json` a required file in the release artifact. It was listed under `OPTIONAL_FILES`, so `release.py` would build a deployable bundle without the config — a board flashed from that artifact has nothing to load at boot and fails fast on the device with a failure that is hard to diagnose from the field. It is now in `REQUIRED_FILES` and a missing `config.json` stops the build with the same "Missing required file" error as every other required file. Build tooling only; no firmware behavior, `config_schema_version`, or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.35 → 0.4.36.

- **Unreleased** (firmware 0.4.34 → 0.4.35): Hardened Core 1's liveness heartbeat against healthy-but-slow device operations, so Core 0's 30 s stale-heartbeat watchdog can no longer reset the board because Core 1 was legitimately busy rather than wedged. Two gaps closed, using the progress-boundary strategy the startup path already used: (1) runtime device reinitialization (a device whose read failures reached the threshold, retrying `initialize()` mid-run) now invokes the same optional `activity_refresh` callback at the same progress boundaries the startup initialization path uses — before each attempt and before each retry sleep — instead of running its whole retry sequence (attempts × `device_initialization_retry_delay_ms`) without refreshing the stamp; (2) the periodic 5 s heartbeat now re-captures `time.ticks_ms()` when comparing and stamping, instead of using the `now_ms` captured before the device read — the same stale-clock correction the read-boundary skip already applies via `skip_now_ms` — so a slow read that carries a heartbeat boundary due in flight stamps the post-read time rather than the pre-read one (which could miss the boundary on that pass and, for a read longer than the 30 s bound, present a healthy Core 1 as stale to Core 0). A driver wedged inside a single `read()`/`initialize()` call still stops the refreshes and is caught by the watchdog, exactly as intended: the refreshes happen at progress boundaries, never inside the driver call. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.34 → 0.4.35.

- **Unreleased** (firmware 0.4.33 → 0.4.34): Fixed Core 0 silently discarding command responses that failed serialization. `_publish_core0_command_response` reported no outcome — a successful publish and a permanent serialization failure both returned the same way — so its two callers could not tell the cases apart. It now returns `True` when the response was published and `False` on a permanent (non-`MemoryError`) serialization failure (a `MemoryError` still propagates to the final recovery boundary). A queued Core 0 command response that fails to serialize is no longer discarded: the command was accepted and its acknowledgement is owed, so the response stays in the pending queue and is retried on a later pass — the same way a failed publish (which raises) already left it pending. And a reboot whose success acknowledgement fails to serialize is now held — no `machine.reset()` without a published response, the reboot stays pending and is retried on a later pass — instead of falling through to `machine.reset()` and rebooting the board without ever answering the command. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.33 → 0.4.34.

- **Unreleased** (firmware 0.4.32 → 0.4.33): Added the final runtime recovery boundary for Core 0. Core 0's fail-fast policy (a `MemoryError` re-raised through every generic handler) was a local rule with no system-level counterpart: Core 0's heartbeat watchdog recovers a dead Core 1, but nothing supervised Core 0 itself, so a Core 0 that terminated — a `MemoryError`, an unexpected parser failure, any exception escaping `start()` or `run()` — left the board with no networking, no Core 1 supervision, and no recovery, turning a transient failure into a permanent outage until something external reset the Pico. `main()` now splits startup into two phases with different contracts: **deterministic startup validation** (hardware detection, config loading/splitting, Core 0 construction) stays outside the boundary and fails fast — a misconfigured or unsupported board must stay down with a diagnosable error rather than reboot forever — while the **operational runtime** (`Core0.start()` through `Core0.run()`, including the Core 1 thread start) is inside the boundary, where an unrecoverable Core 0 exception is a controlled `machine.reset()` instead of permanent application termination. The `MemoryError` handler performs no allocation (it resets immediately, because a diagnostic line would itself be an allocation on an exhausted heap and a raising handler would defeat the reset), while the generic `Exception` handler logs one diagnostic line first (safe, since by construction the failure is not heap exhaustion) and then resets; `machine.reset()` never returns on hardware, so neither handler falls through. Core 1 gating is preserved — if `start()` fails, the Core 1 thread never starts. `core0.py` docstrings updated accordingly (a `MemoryError` propagating out of `start()` now terminates in this boundary as a controlled reset). Failure-path behavior change (no `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.32 → 0.4.33).

- **Unreleased** (firmware 0.4.31 → 0.4.32): Added Core 0-owned duplicate command suppression. `command_id` is the idempotency key — exact, case-sensitive, and opaque (never normalized) — and the first accepted use of an ID owns it until eviction regardless of command name, payload, or target casing. Core 0 retains the 16 most recently accepted command IDs (`core0._RECENT_COMMAND_ID_CAPACITY`) in a fixed-size RAM FIFO, and a command whose ID is still retained is silently ignored — no execution, no Core 1 event admission, no response, and no change to a pending reboot — covering Core 0 commands (reboot) and Core 1 commands (get-details) alike. The check runs at command ingress, after topic/`message_type`/target/identity validation and before schema/payload validation, reboot handling, and event admission: a non-matching target or an invalid `command`/`command_id` keeps its existing early return and consumes no cache entry, a duplicate receipt neither refreshes the entry's FIFO position (last accepted distinct IDs, not LRU access order) nor triggers a response replay (no prior response is retained or resent), and an ID evicted by 16 newer distinct IDs may be processed again. The cache is RAM-only — reboot clears it and it is never persisted to flash — and a suppressed ID emits a DEBUG-only diagnostic, not a production warning. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.31 → 0.4.32.

- **Unreleased** (firmware version unchanged): Added `mqtt_outbound_publish_delay_ms` (default 100 ms, `0` disables) — a Core 0-owned minimum gap between consecutive outbound application MQTT PUBLISHes. The interval begins when the previous QoS 1 publish completes (matching PUBACK received), the first publish after idle/reconnect is immediate, and a failed publish records nothing. The gate is one completion timestamp plus a `ticks_diff`-based readiness check (`core0._mqtt_publish_ready`), applied to every outbound application publish — queued telemetry/health/log/command responses, connection logs, Core 0 command responses, UTC info requests, startup probes — while MQTT protocol-control traffic (PINGREQ, etc.) is never paced. During the runtime it is state, not a sleep: `Core0.run()` keeps looping (Core 1 watchdog, command polling, keepalive, recovery) while the gate is closed and simply begins no new PUBLISH until it reopens, so a backlogged queue drained after a reconnect flows progressively instead of as a broker-speed burst. Only the sequential startup contract waits for a slot (bounded 10 ms slices): the network probes wait for the slot, the startup connection-log drain paces its logs (replacing the fixed 50 ms post-publish sleep), and the startup UTC request respects the interval. A pending reboot holds (no early reset, no bypass) until its response publish slot opens, then proceeds through the existing 5-second grace and `machine.reset()`. Queue FIFO order, admission, heap-reserve bounds, eviction, QoS 1 in-flight retry identity, and run-loop priority are unchanged. `config_schema_version` 6 → 7 (one new required top-level key); `message_schema_version` and `FIRMWARE_VERSION` unchanged.

- **0.4.31**: Cleaned up four low-cost inefficiencies on Core 1's hot path and the startup-log admission path. (1) Deleted the dead `DeviceManager._devices_by_id` state — it was populated for every initialized device but never read at runtime, costing a retained dictionary entry per device with no lookup value (YAGNI; reintroduce if an ID lookup appears). (2) `DeviceManager.get_active_devices()` now returns the internal membership list itself instead of copying it on every telemetry cycle: Core 1 exclusively owns device membership (only the manager mutates it, and only at startup — reinitialization never adds or removes entries), and the sole caller iterates it read-only in Core 1's loop, so the per-cycle `list()` copy was pure heap churn (allocation, not a new wrapper or iterator type). (3) `is_json_safe()` now tests floats with `math.isfinite()` instead of converting every ordinary telemetry float to a string and substring-searching for `"inf"` — same semantics (NaN and ±inf rejected, finite values accepted) with no per-value allocation on the float-heavy validation hot path. (4) Startup-log admission now honors the 0.4.30 admission contract: `_try_queue_startup_log()` raises `ValueError` for rejections that can never succeed on retry (validation failure, oversized, serialization failure, or a permanent queue rejection) instead of returning `False`, and the single caller (a new `_admit_startup_log()` helper) fails fast with the actual reason — previously it unconditionally slept 100 ms and re-submitted the exact same object, a retry that could never change a deterministic outcome. Only the genuinely transient rejection (the `False` heap-pressure return) is retried once, exactly as before. Failure-path behavior change on the startup log's permanent-rejection case (same fatal `RuntimeError` outcome, no pointless wait or second submission); no `config_schema_version` or `message_schema_version` change.

- **0.4.30**: Made a permanently oversized command response unable to stall the Core 1 command channel. The queue API conflated two different failure outcomes into one `False` return: a transient heap-pressure rejection (retrying may succeed) and a permanent rejection of the message itself (serialized beyond `MAX_OUTBOUND_MESSAGE_BYTES`, or a serialization failure — retrying can *never* succeed). The Core 1 command loop retries its pending response forever and processes no further inter-core events while one stays pending, so a response that could never be admitted (a `get-details` snapshot that grows past the 16 KiB ceiling as devices and sections are added) livelocked the channel: endless re-serialization of the same large message (a GC hot loop) with every later command queued behind it. `put()` and `put_with_kind()` now share one failure contract: **`False` is returned only for the transient heap-pressure rejection; permanent rejections (unsupported values, serialization failure, oversize) raise `ValueError`** — extending the convention `put()` already used for its validation errors, with the `oversized_rejected`/`serialization_rejected` counters and untouched queue state preserved. Core 1 uses the distinction: the pending-response loop now answers a permanently rejected response with a small error response for the same command (`success: false`, `error.code: "response_too_large"`, preserving `command_id`/`command`/`targeted` — a few hundred bytes, far under the ceiling) and moves on, while a transiently rejected response (or the substitute itself, under heap pressure) stays pending for a later pass exactly as before. An oversized telemetry sample is discarded with a warning (a current sample is not a replayable record), and the startup log / health message keep their existing fatal / discard policies. Invariant: an individual command response can never permanently block the command channel. Failure-path behavior change (no `config_schema_version` or `message_schema_version` change; one new `error.code` value on the command response wire).

- **0.4.29**: Covered Core 1's initial startup with the liveness heartbeat. `core1_main()` previously registered `core_1_activity_ms` only after device initialization and startup-log admission, and the Core 0 watchdog (`_watch_core_1_heartbeat`) is a no-op until the first stamp exists — so a Core 1 that started its thread and then wedged inside driver construction or a device `initialize()` call was indistinguishable from a Core 1 that had not started yet, and the watchdog could never fire (the shipped system-information driver does not hang, but a future physical I2C/SPI/UART sensor driver could). `core1_main()` now stamps the mailbox at the top of its body, before `SystemInformation`/`DeviceManager` construction and before `initialize_devices()`. Because a legitimately long initialization (several devices × attempts × retry delays) must not age the stamp past the 30 s bound, Core 1 also hands `DeviceManager` an optional `activity_refresh` callback (the same optional-callback pattern `Wifi`/`Mqtt` receive for `wait_service`) that `DeviceManager` invokes at each initialization progress boundary — before each device and before each `initialize()` attempt. The refresh stops precisely when a driver call stops returning, so a wedge is still caught; the default `None` leaves existing `DeviceManager` construction unchanged. Failure-path behavior change (no `config_schema_version` or `message_schema_version` change).

- **0.4.28**: Made the status snapshot's `active` count report devices actually in the READY state, not all devices in the active lifecycle list. `DeviceManager.get_status_snapshot()` computed `active_count = len(self._active_devices)` — but a device that accumulates `device_read_failure_threshold` read failures is marked `reinitialize_pending` and intentionally *stays* in `_active_devices` (it must remain eligible for reinitialization), so `active` counted a device that is not currently producing reads. Health consequently reported `devices_active == devices_configured` and `device_failures == 0` for a device that had stopped reading, avoiding the `device_count_mismatch` degradation reason even though the device was unavailable. The count now sums devices whose state is `DEVICE_STATE_READY` (the lifecycle membership is unchanged). This corrects the documented contract (`devices_active`: active/ready; `device_failures`: configured − active) across health telemetry, `get-details`, and system-information output; a ready device still counts as active, and a device returns to active after a successful reinitialization. Behavior fix (no `config_schema_version` or `message_schema_version` change).

- **0.4.27**: Made the Core 1 heartbeat watchdog serviced during network connect/reconnect waits, closing the P1 class where the watchdog was blind exactly while recovery was in progress. `_watch_core_1_heartbeat()` previously ran only at the top of the Core 0 run loop, but `establish_network()` — the shared startup and mid-run recovery path — contains long monolithic waits (each Wi-Fi attempt's 20 s observation window, retry backoffs up to 40 s, the whole sequence repeating unboundedly). A Core 1 that died together with the network (an outage is the likeliest common cause) therefore aged its stamp only when the network eventually returned — and never, if it never did: a dead core with no reset. Core 0 now exposes one servicing hook, `_service_wait()` (which runs the heartbeat check), and passes it to `Wifi` and `Mqtt` as an optional `wait_service` callback and uses it itself: the sequence-exhaustion backoffs in `establish_network()`, the startup-verification retry sleep, the `Wifi.connect()`/`Mqtt.connect()` retry backoffs, and Wi-Fi's 20 s per-attempt polling loop now all sleep/observe in 100 ms slices with the hook invoked between slices, so a stale heartbeat resets the board *during* the recovery wait. The check is a no-op before Core 1's first stamp, so it is equally safe in the unbounded startup connect loops. `machine.reset()` never returns on hardware, so the hook can never be "swallowed" by the connect loops' exception handlers in production. Failure-path behavior change (no `config_schema_version` or `message_schema_version` change).

- **0.4.26**: Replaced the count-bounded queues with heap-reserve-bounded queues. The fixed capacity rules (outbound 16-entry count + 32 KiB aggregate byte budget; event 4-entry count) are gone: both FIFO lanes are now admitted against the global minimum free-heap reserve, sourced from `hardware.py` (64 KiB Pico W, 128 KiB Pico 2 W) — the single source of truth for queue memory safety, not deployment-configurable. `InterCore` now takes `minimum_free_heap_bytes` (from `main.py`'s early `detect_hardware()`) and creates one shared heap-admission lock, passed to both queues, that serializes the heap measurement, the pressure-path `gc.collect()`, and the eviction/admission decision — because the MicroPython heap is global to both cores. Outbound admission: fast path admits with no garbage collection when `gc.mem_free() >= reserve`; the pressure path collects once, and if the reserve is still not restored evicts the oldest entry in the least-important eligible queued class (only when the incoming entry is at least as important), reclaims, and rechecks — repeating until the reserve is restored or nothing eligible remains — then admits or rejects. The in-flight QoS 1 entry is never an eviction candidate, and priority/oldest-first semantics are otherwise unchanged. The event queue uses the same reserve and lock but never evicts an admitted event (discrete control operations): under pressure the new event is rejected and Core 0 reports the new `intercore_event_queue_memory_pressure` error code. The 16 KiB per-message ceiling (`MAX_OUTBOUND_MESSAGE_BYTES`) is retained and enforced on both admission paths. Retired: the `max_outbound_queue_entries`/`max_intercore_event_entries` config keys (`config_schema_version` 6 — configs carrying them fail fast as unknown keys), the `outbound_queue_capacity`/`outbound_queue_utilization_percent`/`outbound_max_queued_bytes`/`outbound_queue_byte_utilization_percent` health fields, the `outbound_queue_pressure` degradation reason (a below-reserve heap is itself the pressure condition, reported as `low_free_heap`), and `split_config()`'s third `bus_config` return value. Added health fields: `outbound_queue_high_watermark`, `outbound_queue_high_watermark_bytes`, `outbound_evicted`, `telemetry_evicted`, `outbound_rejected` (depth and `outbound_queued_bytes` retained); `SystemInformation.get_queues()` exports the same observability view plus the event-queue pending/high-watermark/rejected counters. `OutboundQueue.status()` now reports the depth/bytes high watermarks and eviction/rejection counters in place of the old capacity views; the queue-internal byte accounting (in-flight bytes retained until PUBACK) is unchanged. `MemoryError` propagation semantics are preserved throughout. `config_schema_version` bumped to 6 (no `message_schema_version` change).

- **0.4.25**: Made command target matching case-insensitive. `Core0._target_matches()` compared the command `target` against the configured `source` with exact string equality, so a logically equivalent casing variant (e.g. `teSt-PICO-2` for a device configured as `Test-Pico-2`) silently failed to match and the command was ignored with no response. The source comparison now normalizes both sides with `lower()` (MicroPython-safe, no `casefold()` dependency) at the comparison boundary only: the stored/configured source keeps its original casing, responses are still emitted with the configured casing via `_envelope_fragment()`, and the broadcast (`*`) and IP-address targeting paths are unchanged. A non-string `target` still simply fails to match (an `isinstance` guard preserves that without raising where `lower()` would). Applies to every command on the shared routing path; no command-specific logic. Behavior fix (no `config_schema_version` or `message_schema_version` change).

- **0.4.24**: Added the Core 1 `get-details` command. The command requires an empty payload and returns a current full system-information snapshot directly in `command_response.payload.data`, collecting every section named by `SYSTEM_INFORMATION_SECTIONS` regardless of the configured `system-information` telemetry device `include` list. The implementation reuses the existing full-system-information collector used by the startup log, preserving one source of truth for section collection and the existing per-section error behavior. Additive command behavior only; no config or message schema version change.

- **0.4.22**: Made the 16 KiB per-message ceiling a queue invariant on both admission paths, not just a property of the `put()` serialization path. `put()` enforces it via `serialize_and_validate_message()` (a `MessageTooLargeError` rejection), but `put_with_kind()` — the pre-serialized-bytes path both production callers (startup log, health message) use — passed bytes straight to `_admit_locked()` with no per-message size check: the 32 KiB aggregate byte budget therefore admitted a single entry of up to 32 KiB through that path, invalidating the 16 KiB transient-peak rationale (graph + str + bytes ≈ 3x the payload ≈ 48 KiB) both memory bounds are sized against. Both shipping callers serialize first and were safe, so this closed an invariant gap (two sources of truth for the memory rule) rather than a live defect. `put_with_kind()` now rejects any payload longer than `MAX_OUTBOUND_MESSAGE_BYTES` — the same constant `put()` enforces — incrementing the existing `oversized_rejected` counter and leaving queue state untouched, exactly like the `put()` path. No re-parsing or JSON allocation (a length check on final bytes), and the caller contract (bytes are already validated, serialized JSON) is unchanged. Failure-path behavior change (no `config_schema_version` change).

- **0.4.21**: Made the outbound byte budget account for the in-flight entry's retained bytes, so the budget now caps ALL payload bytes the outbound queue retains, not just the queued FIFO. The in-flight entry is popped out of the FIFO by `take()` and held until its PUBACK (`complete_in_flight`), so its payload bytes stay resident the whole time — but `take()` subtracted them from the byte count the moment the entry moved in-flight and `complete_in_flight()` never re-added them. The budget therefore capped only the queued FIFO: a 16 KiB in-flight payload plus a full 32 KiB of queued payloads could be resident at once (48 KiB) while `outbound_queued_bytes` reported only 32 KiB, and admission kept granting the full 32 KiB of queued room on top of whatever was in flight. Now `take()` leaves the entry's bytes counted, `complete_in_flight()` releases exactly the completed entry's bytes, and eviction subtracts queued entries as before — the in-flight payload consumes budget for as long as it is retained. This tightens the worst-case retained payload from 48 KiB to 32 KiB and makes the two budget views consistent: `outbound_queue_depth` already included the in-flight entry, and `outbound_queued_bytes` now does too. `outbound_queued_bytes` (health and startup log) can now read slightly higher while an entry is in flight; `outbound_max_queued_bytes` is unchanged. Steady-state memory-boundary change (no `config_schema_version` change).

- **0.4.20**: Made a Core 0 command/reboot response retry the same wire document, not just the same sequence identity. 0.4.17 made `(runtime_id, sequence)` a reliable unique event identity by claiming the sequence before the first transmission attempt and stamping it on the logical object so a retry reuses it — but for Core 0's own retryable responses (the pending command responses and the pending reboot) the identity was preserved while the *content* was not: `_publish_core0_command_response()` rebuilt the message (re-capturing `uptime_ms` and `timestamp`) and re-serialized it on every attempt, so an ambiguous QoS 1 failure (the PUBLISH reached the broker but the PUBACK was lost) followed by a retry put two packets with the *same* `(runtime_id, sequence)` on the wire carrying *different* documents (differing `uptime_ms`/`timestamp`). A downstream deduplicator keyed on that identity could then discard one of two differing documents depending on arrival order. Queued telemetry never had this problem because its pre-serialized bytes stay attached to the same in-flight queue entry. The serialized bytes are now frozen on the persistent logical object on the first attempt (a new `container` parameter on `_publish_core0_command_response()`, the pending response dict or the pending reboot dict, mirroring the queue's in-flight entry) and re-published verbatim on a retry, so a retry is the same logical message with the same identity AND the same content. The wire format and the QoS 1 at-least-once guarantee are unchanged; only the pathological ambiguous-failure-then-retry case now emits byte-identical frames. Failure-path behavior change (no `config_schema_version` change).

- **0.4.19**: Made the disposal of a failed MQTT client bounded too, closing the last unbounded write on Core 0's network path. 0.4.16 bounded the QoS 1 PUBLISH frame writes and the PUBACK wait, but the cleanup of the client left behind after such a failure was not: `Mqtt._close_old_client()` — the first step of every `connect()` attempt, i.e. of every reconnect — called `MQTTClient.disconnect()`, which unconditionally wrote an MQTT DISCONNECT frame. After a failed bounded exchange, the exchange's `finally` had already restored the socket to infinite-blocking mode, so that DISCONNECT write into the already-failed link had no deadline: on a blackholed link (TCP up, sends not draining) it wedged Core 0 inside `sock.write()` forever, and with Core 0 wedged its Core 1 heartbeat watchdog (0.4.9) could never run either — the same P1 class 0.4.16 fixed for the PUBLISH itself, one step later in the failure chain (publish stalls → bounded timeout → socket restored to infinite blocking → reconnect → unbounded DISCONNECT write → permanent wedge). Disposal now closes the TCP socket directly with no write at all: this path only ever runs while the session is not connected (`connect()` is only entered from `establish_network()`'s `while not is_connected()`), so the old client is always failed or never established and no graceful DISCONNECT frame is needed — the broker drops the clean session when the TCP connection closes. Failure-path behavior change (no `config_schema_version` change).

- **0.4.18**: Made the queued-byte budget visible to system telemetry and health, so the queue's memory-protection boundary can no longer be full while health reports no pressure. The byte budget (0.4.8: 32 KiB of queued payload bytes, enforced alongside the 16-entry count) was only ever reported as entry counts: `SystemInformation.get_queues()` (the startup-log source) and the health payload both carried no byte view, and `outbound_queue_pressure` was computed from entry utilization alone — a handful of large entries (e.g. 4 × ~8 KiB) could sit at 25% entry utilization while the byte ceiling was at 100%, the exact condition the budget exists to flag. The health payload now carries `outbound_queued_bytes`, `outbound_max_queued_bytes`, and `outbound_queue_byte_utilization_percent` (sourced from a new single-lock `OutboundQueue.get_health_metrics()` reading both budget views consistently), `SystemInformation.get_queues()` now exports the two byte fields, and `outbound_queue_pressure` fires at `max(entry_utilization, byte_utilization) >= 75%`. Queued bytes exclude the in-flight entry, matching the byte admission budget in `_admit_locked`; the entry-depth field still counts it, as before. The byte-utilization computation is integer-only (MCU-safe), no new config or schema surface. Additive wire change (three new health payload fields); no `config_schema_version` change.

- **0.4.17**: Made the wire `sequence` reliable across an ambiguous QoS 1 failure. The sequence was consumed only after a successful PUBACK, so in the ambiguous case — the PUBLISH reached the broker but the PUBACK was lost — the number was never consumed and was handed out again: a `mqtt_connection_established` log published after the reconnect took the in-flight telemetry's sequence (a `(runtime_id, sequence)` collision on the wire), and the telemetry retry then took a still-newer one, so the same logical sample appeared under two identities and an unrelated message reused the sample's number. The sequence is now claimed before the first transmission attempt and stamped on the logical object — the queue entry, or Core 0's persistent response/reboot dict for its own retryable messages (`_claim_wire_sequence` in `core0.py`) — and is never rolled back: a retry of the *same* logical message reuses the stamped number (both copies identify one message, legitimate QoS 1 duplicate delivery), while a *different* message always gets a fresh number. `(runtime_id, sequence)` is therefore now a safe unique event identity and a retry is recognizable as the same message. The wire format is unchanged (same top-level keys, same Core 0 values) and the QoS 1 at-least-once delivery guarantee is unchanged. Failure-path behavior change (no `config_schema_version` change).

- **0.4.16**: Bounded the QoS 1 PUBLISH frame writes, not just the PUBACK wait. `MQTTClient.publish()` installed the socket timeout only *after* all four socket writes (header, topic, packet id, payload), so a link failure that leaves TCP apparently established while sends stop making progress wedged Core 0 inside `sock.write()` — and with Core 0 wedged, its Core 1 heartbeat check (the 0.4.9 watchdog) never ran, leaving no recovery path. The timeout is now installed before byte 1 of the frame and restored only after the exchange finishes, so the frame writes and the PUBACK wait share one bounded deadline: a stalled write surfaces as a bounded error into `Mqtt.publish_qos1`'s disconnect + network recovery (the entry stays in flight, at-least-once semantics unchanged). Wire order (header, topic, packet id, payload) and the QoS 0 path are unchanged; a failed timeout installation now aborts before any byte is transmitted instead of after the full frame. Failure-path behavior change (no `config_schema_version` change).

- **0.4.15**: Made `MemoryError` propagation consistent on the Core 0/Core 1 message paths. Heap exhaustion is a fatal condition, not a failed optional diagnostic, but several allocation-heavy paths swallowed it in a generic `except Exception` handler and kept the core running on top of an exhausted heap: `core1._collect_system_information_full()` (a failed section was recorded as `{"error": ...}`), `core1._try_queue_startup_log()` and `core1._try_queue_health_message()` (the message was silently discarded as if serialization had merely failed), `core1._build_health_payload()` (heap/hardware fallbacks), the Core 1 startup hardware storage, `core0._service_pending_connection_log()`, and `core0._publish_core0_command_response()` (whose handler was `except (MessageTooLargeError, Exception)` — effectively `except Exception`). Every one of these now re-raises `MemoryError` before the generic handler, matching the convention every other module already followed. Heap exhaustion now stops the core with a diagnosable error instead of obscuring the root cause or making fragmentation worse, and the callers' existing `except MemoryError: raise` clauses (e.g. `_perform_reboot`) can now actually fire. Ordinary (non-`MemoryError`) failures are still handled as before: reported and the message discarded. Failure-path behavior change only (no `config_schema_version` change).

- **0.4.14**: Stopped the telemetry scheduler from replaying missed boundaries as catch-up reads. When a device read stalled long enough to cross one or more `read_loop_sec` boundaries, the deadline advanced by a single interval per pass, so the loop fired an extra read almost immediately — and another, until it caught up: a burst of near-identical current samples, JSON work, and queue admissions landing right after the overload. Telemetry is a current sample, not a replayable record, so a stall cannot reconstruct the missed samples; the scheduler now performs the current sample once and skips directly to the next future boundary — the same missed-boundary policy the health scheduler already used. The skip is evaluated against a clock re-read after the read completes, because the loop's captured clock is stale by however long the read took and would otherwise under-advance and leave a catch-up read for the next pass. Outage buffering is unchanged (an MQTT outage still queues telemetry rather than dropping it); this only changes the pathological slow-read case. Static behavior change (no `config_schema_version` change).

- **0.4.13**: Eliminated the double serialization on the publish path. A queued message was serialized by its sender and then, on Core 0, decoded, parsed back into a dict, merged with Core 0's envelope fields, and re-serialized as a whole document (`dict → str → bytes → queue → str → dict → str → MQTT`): the message body was serialized twice, and the transient allocations, CPU, and fragmentation risk accumulated exactly where the queue was supposed to improve memory predictability. The contract is now: the sender carries its complete message — including `uptime_ms` and `timestamp` (null when UTC is unsynchronized) — and must not carry any envelope key at the top level (`sequence`, `runtime_id`, `source`, `firmware_version`, `message_schema_version`); Core 0 injects those five members at publish time by splicing them into the stored serialized object before its closing brace. The payload is never decoded, parsed, or re-serialized on the publish path, so publishing allocates only the small envelope fragment plus the assembled frame. The wire format is unchanged (same top-level keys, same Core 0 values) and the queue still stores immutable pre-serialized bytes — the frame is a fresh allocation, the entry is untouched. Core 1 no longer pre-embeds `runtime_id`/`source`/`firmware_version`/`message_schema_version` (they were always overwritten by Core 0 anyway), and the health/startup-log `timestamp` is computed from the shared UTC snapshot instead of being left null for Core 0 to fill (which required the parse it could no longer afford). Static behavior change (no `config_schema_version` change).

- **0.4.12**: Bounded the inbound MQTT packet size. `wait_msg()` now rejects a PUBLISH whose remaining length exceeds `MAX_INBOUND_PACKET_BYTES` (16 KiB — the same MCU-scale ceiling as the outbound limit) *before* allocating its payload: previously `sock.read(sz)` was handed whatever the broker's remaining-length field claimed, and a broker-side bug publishing an oversized command/info response could request an allocation large enough to exhaust the Pico W's RAM (no hostile traffic required). An oversized frame — like a fifth remaining-length byte (an MQTT protocol violation that was previously an unbounded read loop) — now closes the socket and raises `MQTTException`, which the `Mqtt` layer turns into a marked disconnect and Core 0's existing recovery path reconnects, instead of trying to buffer or drain the corrupt stream. Static constant (no `config_schema_version` change).

- **0.4.11**: Fixed the MQTT receive path parsing incoming packets in non-blocking socket mode. `check_msg()` now decides *readiness* with a non-blocking `select` poll — one readable byte means a packet has started; nothing returns `None` immediately and leaves the socket mode untouched — and only then parses the packet on a blocking-with-finite-timeout socket bounded by `mqtt_broker_response_timeout_sec`. Previously the whole multi-byte parse ran non-blocking, and because MicroPython documents that `read(n)` may return fewer bytes than requested in non-blocking mode, a PUBLISH split across TCP reads could short-read its topic or payload and deliver a corrupt frame (or raise a spurious disconnect) instead of waiting for the rest of the packet. Now a link that stalls after the first frame byte surfaces as a bounded timeout into the existing recovery path, and a ready packet is always fully read. `wait_msg()` and the bounded-wait invariants are otherwise unchanged; `check_msg()` now installs and restores its own finite timeout like `publish`/`ping`. Static behavior change (no `config_schema_version` change).

- **0.4.10**: Made startup verification self-healing to match the (already) unbounded connect loops. Previously the QoS 1 probes and UTC sync were the only fail-fast steps: a single transient blip after connection — a dropped PUBACK on a probe, or a brief UTC-server outage across the 3 bounded attempts — raised `RuntimeError` out of `core0.start()`, exited `main()`, and left the device stopped until a physical reset, even though a broker that was *never* reachable would have looped forever. `start()` now keeps the verification steps (probe #1 → drain → 5 s wait → probe #2 → UTC) in a new `_verify_startup_contract()` pass inside a retry loop: on any pass failure it drops the MQTT session (`mark_disconnected()`), re-establishes the network, and retries the whole pass, reusing the existing `mqtt_reconnect_delays_sec` backoff. Core 1 stays gated because `start()` has not returned and `_network_stack_ready` is set only after a clean pass; a `MemoryError` still propagates (fail-fast) so an out-of-memory device is not looped. Static behavior change (no `config_schema_version` change).

- **0.4.9**: Core 0 became the independent consumer of the Core 1 liveness heartbeat, closing the P1 failure mode where a dead or wedged Core 1 thread (an unhandled `MemoryError`/`Exception`) wedged the whole sensor — telemetry and health silently stopped, a dead Core 1 could not build the health message that would report `core_1_inactive`, and Core 0 kept running indefinitely with no recovery. The Core 0 run loop now checks `core_1_activity_ms` first on every pass (`_watch_core_1_heartbeat` in `core0.py`): before any stamp exists (Core 1 has not started) the check is a no-op, so the unbounded startup connect loops are unaffected; once a stamp exists, age at or beyond `_CORE_1_HEARTBEAT_STALE_TIMEOUT_MS` (30 s — more than six missed 5 s refreshes, and below the 60 s `core_1_inactive` diagnostic threshold) logs FATAL and calls `machine.reset()`. Static constant (no `config_schema_version` change).

- **0.4.8**: Made the outbound message/queue limits MCU-safe. The per-message ceiling dropped from 128 KiB to 16 KiB (`message_serializer.MAX_OUTBOUND_MESSAGE_BYTES`) — the check runs after `json.dumps()` + UTF-8 encode, so the object graph, serialized `str`, and encoded `bytes` are all resident at once and a 128 KiB payload could not be admitted safely on a Pico W; 16 KiB bounds a single message's transient peak (~48 KiB) with margin over the largest legitimate message (the startup log). `OutboundQueue` is now bounded by BOTH entry count and an aggregate queued-byte budget (`DEFAULT_MAX_OUTBOUND_QUEUED_BYTES` = 32 KiB), so 16 retained payloads can no longer exhaust heap on their own; admission enforces both budgets and only evicts when it frees enough room (by count or bytes), never dropping a valid entry to admit one that would not fit. Both bounds are static constants (no `config_schema_version` change); `OutboundQueue.status()` now also reports `queued_bytes` and `max_queued_bytes`.

- **0.4.7**: Fixed the MQTT handshake blocking indefinitely: `Mqtt.connect()` now passes `mqtt_broker_response_timeout_sec` to `MQTTClient.connect()`, bounding the CONNACK wait — and, since `subscribe()` inherits that socket timeout, both SUBACK waits. A broker that accepts the TCP connection and then stops responding now fails the connect attempt (retried with the reconnect backoff) instead of wedging Core 0 forever; the socket returns to normal blocking mode once both subscriptions succeed.

- **0.4.6**: One shared normal-runtime scheduling epoch for all periodic Core 1 work. `normal_runtime_start_ticks_ms` is captured exactly once, immediately after `system_startup_completed` is admitted to the outbound queue; both the telemetry deadline (`anchor + n × read_loop_sec`) and the health deadline (`anchor + n × health_interval_sec`) derive their fixed boundaries from that anchor. Telemetry and health remain independent schedulers (shared epoch, no execution dependency); neither deadline derives from the other. `boot_ticks_ms` remains the boot-lifetime reference for uptime (`uptime_ms`) and startup-duration measurement only. Reconnects, UTC resyncs, and device reinitialization never reset the anchor; only a reboot creates a new one. Health outage policy is unchanged (missed intervals skipped, never replayed); telemetry outage buffering is unchanged.

- **0.4.5**: Health scheduling anchored to boot time: `health_interval_sec` now defines fixed uptime-based boundaries from firmware boot (60s interval → first health at ~60s uptime, then 120s, 180s, ...). The immediate post-startup health message is removed; boundaries missed during startup or an MQTT outage are skipped, never replayed; deadlines advance from the previous boundary so processing delay cannot accumulate drift.
