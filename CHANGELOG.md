# Changelog

This document records notable changes to the project across released versions.

Changes are organized by version in reverse chronological order, with the most recent release listed first. Each version should summarize meaningful changes such as new features, fixes, behavioral changes, refactoring, configuration changes, and other updates relevant to developers or operators.

## Versioning

Project versions follow Semantic Versioning where practical:

- **MAJOR** — incompatible or breaking changes
- **MINOR** — backward-compatible features or significant enhancements
- **PATCH** — backward-compatible fixes, maintenance, and small improvements

## Change Categories

When applicable, changes should be grouped under clear categories such as:

- **Added**
- **Changed**
- **Fixed**
- **Removed**
- **Deprecated**
- **Security**

## Version History

- **Unreleased** (firmware 0.4.86): **Added the `bme280` device — the first hardware (I2C) sensor** — The device framework previously shipped only the software-only `system-information` sensor. A new `bme280` `device_type` drives a Bosch BME280 (temperature, barometric pressure, relative humidity) over I2C, following the established device-driver pattern. `devices/bme280/` is a new package: a pure, host-importable config validator (`validation.py`, `ALLOWED_CONFIG_KEYS` + `validate_config()`), the low-level `BME280` protocol/compensation class, and the `BME280Device` `Device` adapter (`bme280_device.py`). The protocol implements the Bosch data sheet exactly: chip-ID verification (`0xD0` must read `0x60`; a BMP280 shares the addresses, so an ACK alone is rejected), the software reset, a finite NVM-copy wait, the two-block calibration read (little-endian signed 16/12/8-bit, `dig_H4`/`dig_H5` decoded from their shared register `0xE5`), the `ctrl_hum` → `config` → `ctrl_meas` write-latch order, temperature/`t_fine` computed before pressure/humidity (which consume it), the single coherent 8-byte burst read from `0xF7`, Bosch floating-point compensation (Pa / °C / %RH), disabled-channel sentinels returned as `None` rather than fed to the equations, a pressure divide-by-zero guard, humidity clamped 0–100, and a conversion delay computed from the oversampling. It runs in forced mode (init leaves the sensor asleep; each `read()` triggers one conversion). `BME280Device` applies the application-layer policy kept out of the fundamental compensation: user `offsets.{temperature_c, humidity_percent, pressure_pascal}` after Bosch compensation, and a derived `altitude_m` from the offset-adjusted pressure and `sea_level_pressure_pa`. Telemetry is `{temperature_c, pressure_pa, humidity_percent, altitude_m}` (pressure in Pa; the presentation layer converts to hPa).

  The I2C bus is configured **per device** (`i2c_bus` required; optional `i2c_sda_pin`/`i2c_scl_pin`/`i2c_freq_hz` defaulting to the bus's default pins and 400 kHz) and, per the ownership invariant, Core 1 owns the bus — a driver never creates one. `core1_main` hands `DeviceManager` a bus factory that builds one `machine.I2C` per distinct `(bus, sda, scl, freq)` and caches it (two devices on a bus share one object), importing `machine` lazily inside the closure so a config with no I2C device allocates no bus or pins; `create_device` resolves a device's bus through the factory, which is injected so `device_factory` and `device_manager` stay host-importable. The bus is created at driver construction (peripheral + pins only); the sensor protocol runs in `initialize()`, which the retry/reinit machinery wraps, so an absent/miswired BME280 degrades to a failed device rather than a boot halt. The sensor is addressed by an explicit `i2c_address_candidates` list (default `[118, 119]`, i.e. `0x76`/`0x77`) — each candidate chip-ID-verified, no blind bus scan. Oversampling (0–5) and the IIR filter (0–4) are per-device knobs defaulting to the recommended ×1/×1/×1, filter-off profile; the validator enforces that a fresh pressure/humidity compensation has the temperature channel enabled (its `t_fine` feeds both), that at least one channel is enabled, and that `i2c_sda_pin` ≠ `i2c_scl_pin`.

  `config_schema_version` unchanged (8) — the change is additive at the device level (a new `device_type` and its device-config keys, no new top-level key). The shipped `config.json` gains a `bme280` device. Tests: `tests/test_bme280_validation.py` (pure validation: unknown/missing keys, each bound, the `t_fine` and all-skip rules, `sda == scl`, `initialize()` reuse), `tests/test_bme280_compensation.py` (the integer decode helpers, H4/H5, 20/16-bit ADC reconstruction, register construction, measurement timing, divide-by-zero, humidity clamping, sentinels), and `tests/test_bme280_device.py` (factory support, `create_device` bus resolution, init/read/reinit against a fake I2C, offsets, altitude, and fail-fast on wrong chip ID / zero `dig_P1`); `tests/test_device_validation.py`'s unsupported-type case now uses a genuinely unknown type since `bme280` is supported. Hardware-verified 2026-09-07 on a Pico 2 W (deploy target 2): boots clean end-to-end with both devices (`Core 1 devices initialized: 2/2`, health `healthy`), and the bme280 reports physically consistent `temperature_c`/`pressure_pa`/`humidity_percent`/`altitude_m` telemetry — the derived `altitude_m` is self-consistent with the measured `pressure_pa` under the barometric formula (99001 Pa at `sea_level_pressure_pa` 101325 → ~195 m), independently confirming the Bosch pressure compensation and the altitude derivation on real silicon; a sensor missing its `i2c_sda_pin`/`i2c_scl_pin` correctly degrades to `initialization_failed` with the board healthy.

- **Unreleased** (firmware 0.4.85): **Made an empty `system-information` device `include` list mean "all sections"** — The `system-information` device config's `include` list was required to be non-empty, so reporting every section meant enumerating all nine `SYSTEM_INFORMATION_SECTIONS` entries by hand. The pure validator (`devices/system_information/validation.py`) now accepts the empty list as an **"all sections" shorthand** (a non-list `include` is still rejected — the message drops "non-empty" — and the per-entry string/known-section/unique checks are unchanged), and `SystemInformationDevice.initialize()` expands it: `_include = tuple(config["include"]) or SYSTEM_INFORMATION_SECTIONS`, so `_include` always holds the concrete sections and `read()` is untouched — including the once-only `get_device_sections()` sharing for `devices`/`device_status`. The expansion is driver runtime behavior, never a config rewrite: the on-disk config and `read-config` responses keep the user's `[]` verbatim, and the `get-details` command already reported all sections regardless of `include`. Note the operational effect: with `[]`, each scheduled telemetry pass publishes all nine sections, so the sample is larger than a single-section read (still far under the 16 KiB per-message ceiling; a rejected oversized sample is discarded, as telemetry always is). Tests: `tests/test_device_validation.py` accepts `{"include": []}` at the validator, pins the driver's expansion to `tuple(SYSTEM_INFORMATION_SECTIONS)`, and drops the empty list from both rejection parametrize lists; `tests/test_system_information_device.py` adds an all-sections stand-in and a `read()` test asserting the empty include reports every `SYSTEM_INFORMATION_SECTIONS` section in order with the shared device snapshot taken exactly once. `config_schema_version` unchanged (8).

- **Unreleased** (firmware 0.4.84): **Added a configurable outbound-queue maximum message count (`outbound_queue_max_messages`), and bumped the configuration schema v7 → v8** — The Core 1 → Core 0 outbound queue was heap-governed with no fixed entry count, so its depth was unbounded in principle (a long broker outage could accumulate a large FIFO). `config.py` now requires a new top-level key `outbound_queue_max_messages` (a positive integer bounded at `MAX_OUTBOUND_QUEUE_MAX_MESSAGES`, 256; the shipped value is 64) that sets a **deterministic entry-count ceiling on the outbound queue, subordinate to the existing heap policy**: admission is decided against the board's two heap thresholds first and the heap remains authoritative — the count ceiling can add a rejection or a retention-aware eviction but never admits what the heap would reject — and only at the three heap append sites (normal / soft / hard) once the heap floor is satisfied is the entry count (queued + in-flight, the same depth as the high-water-mark metric) checked against the ceiling. At the limit the queue reuses the *same* retention-aware `_evict_one_eligible_locked()` the heap path uses (no second eviction policy, no FIFO/pop) to free one slot, runs `gc.collect()`, and appends; with nothing eligible to evict it is rejected as transient (the producer retains and retries), counted exactly once through the hard loop's single rejection point. In-flight entries count toward the limit, so `outbound_queue_depth` and `outbound_queue_high_watermark` are now bounded by the ceiling (the byte metrics remain heap-governed only), and a full-of-CRITICAL queue rejects rather than overflowing or reserving slots — the same transient-rejection path the producers already handle (telemetry discards the sample, a command response holds as `pending_command_response` and retries each loop pass), so no new producer code. The key is a bus property set once at construction: `main.py` reads it after `recover()` and passes it to `InterCore(...)` (deliberately kept out of `split_config()`, like the board heap thresholds), and `config_manager.py` classifies it `REBOOT_REQUIRED` — matching the bus-constructed-once design and the `network_probe_timeout_sec` precedent, and keeping the `high_watermark ≤ max` invariant clean across a hot write. It is a deterministic observability/stability bound, **not** a hard capacity or a memory bound: the heap policy remains the memory guard, and the retired fixed-capacity keys `max_outbound_queue_entries` / `max_intercore_event_entries` (removed in schema v7) stay rejected. `OutboundQueue.status()` reports the configured `max_messages` for internal observability (not a health/wire field — the proposal defers that as a non-goal). This is a configuration-schema change (a new required key), so `config_schema_version` bumps **7 → 8** (the `message_schema_version` is unchanged) and the shipped `config.json` and `tests/fixtures/config.json` carry the new key at 64. Tests: `tests/test_intercore.py` covers the ten count cases (below/at the limit, retention-aware eviction selection, no-eligible rejection, CRITICAL saturation, heap-first single eviction under concurrent heap pressure, heap rejection not overridden, high-water-mark ≤ max, small-heap heap-wins, and in-flight counting); `tests/test_config.py` pins accept/reject at the 256 bound and the schema-8 requirement; `tests/test_read_write_config_commands.py`'s schema-version assertion now reads `CONFIG_SCHEMA_VERSION` instead of a hardcoded 7. Also in this release: `core0.py`'s connection-log publish path now also waits on `not outbound_queue.has_in_flight()`, so a pending connection log is held while an outbound entry is still in flight (a retry after a transport failure) and the two publish paths never interleave — a new `tests/test_outbound_publish_pacing.py` case pins it (held while the entry is in flight, publishes once it clears). Plus doc-density comment trims across `config.py`, `intercore.py`, `core0.py`, and `mqtt_client.py` (no behavior change).

- **Unreleased** (firmware 0.4.83): **Validated the SUBACK frame, filtered the broker name resolution to an IPv4 stream, and bounded the Wi-Fi secrets** — `mqtt_client.subscribe()` was the one acknowledgement path that never validated the frame shape it consumed: a single 4-byte read took the SUBACK's remaining length plus body without checking the length, so a declared length other than 3 (the 2-byte packet id + 1 return code of this client's single-topic subscription) was accepted — leaving a stray byte in the TCP stream (or over-consuming the next packet's bytes when the declared length was short) and desynchronizing every later frame — and a reserved return code (anything but 0x80) was treated as a grant. The length byte is now checked before the body is read and the return code gated to the granted QoS codes 0x00–0x02 or 0x80 (failure): a mismatch drops the connection via `_abort_corrupt_inbound` rather than erroring, the same treatment as the CONNACK, PUBACK, and PINGRESP checks. `MQTTClient.connect()` now filters `socket.getaddrinfo()` to `AF_INET`/`SOCK_STREAM` — the profile the default socket constructs — so a broker hostname resolving to multiple records cannot hand `connect()` an unusable first record (IPv6, datagram); the config contract (253-byte hostname maximum, `config.MAX_MQTT_BROKER_ADDRESS_BYTES`) is unchanged. `config.load_wifi_config()` now enforces byte bounds on the Wi-Fi secrets — the SSID at 32 bytes (the IEEE 802.11 SSID limit) and the password at 64 bytes (a 63-character WPA2-PSK passphrase or a 64-hex raw PSK), an embedded NUL rejected in either, and the empty password still legal for open networks — so a misprovisioned `config-secrets.json` fails fast at boot with the field named instead of surfacing deep in the Wi-Fi retry machinery and holding an oversized string in heap. Tests: `tests/test_mqtt.py` covers the malformed SUBACK remaining length (stray byte, and the short-length over-consumption of the next packet's bytes), the reserved return code, and the filtered resolver call and address; `tests/test_wifi_config.py` is new (the bounds at and over the limit, a multibyte SSID over the byte bound but under a character count, NULs, the empty password, unknown keys, and missing fields). `config_schema_version` unchanged.

- **Unreleased** (firmware 0.4.82): **Sliced the reboot grace period so a planned reboot stays a clean reset, and tightened the outbound-queue serializer import** — the 5-second pre-reboot grace in `core0.py` was the one long wait in Core 0's post-arming paths that slept monolithically (`time.sleep_ms(5000)`), so the grace plus the preceding QoS 1 publish wait could stretch past `WDT_TIMEOUT_MS` (8 s) and reset the board via the hardware watchdog instead of the explicit `machine.reset()` — a watchdog trip that was really a planned reboot. It now sleeps in 100 ms slices via `_sleep_and_service()` (the same servicing hook as every other long run-loop wait: the Core 1 heartbeat check and `_feed_watchdog()`), so the grace period stays clean and explorable. Accompanying cleanup: `core1.py`'s `_run_telemetry_read_pass()` drops its unused `config` parameter (both call sites updated), and `intercore.py`'s `message_serializer` import moves from a lazy in-function import to module level (no circular import — `message_serializer` only imports `message_protocol`), which lets the tests monkey-patch `intercore.serialize_and_validate_message` directly. Tests: `tests/test_intercore.py` retargets its serializer monkey-patches at `intercore`; `tests/test_reboot_command.py` stubs `get_core_1_activity_ms` to `None` so the heartbeat check running inside the sliced grace sleep is a no-op, as with the real mailbox before Core 1 stamps one. `config_schema_version` unchanged.

- **Unreleased** (firmware 0.4.81): **Gave Core 0 its own hardware watchdog, and put operational liveness bounds on the recovery-timing config keys** — `core0.py` now arms `machine.WDT` (`WDT_TIMEOUT_MS`, 8 s — under the RP2 8388 ms hardware maximum and over every single bounded wait Core 0 performs) at the end of `start()`, after the deliberately unbounded startup connect/verification loops, which a watchdog would reset into the same waits. Feeding comes only from Core 0's own execution — the run loop (once per pass) and the 100 ms `_service_wait` slices it drives — never from an independent timer, IRQ, or Core 1, so no other subsystem can mask a wedged Core 0; a build without `machine.WDT` degrades to a warning instead of a deterministic reset loop, and a `feed()` failure escapes to `main.py`'s controlled-reset boundary. This complements the existing supervision: Core 0's heartbeat watchdog recovers a dead Core 1, the exception boundary in `main.py` covers what raises, and the hardware watchdog covers a Core 0 that is alive but no longer making progress (ARCHITECTURE.md gained a "Core 0 hardware watchdog" section). The budget invariant is enforced at the config/constant layer: `mqtt.py`'s PINGRESP cap drops 10 s → 5 s, and `config.py` now rejects representable-but-recovery-defeating values on the four recovery-timing keys — `mqtt_broker_response_timeout_sec` ≤ 5 s (every bounded MQTT wait it sizes must fail under the watchdog budget), `network_probe_timeout_sec` ≤ 30 s, `device_initialization_retry_delay_ms` ≤ 60 s, `device_read_failure_threshold` ≤ 1000 — with the shipped values (4 s / 5 s / 250 ms / 3) well below every bound; a write-config candidate carrying such a value is rejected the same way. Two memory-shape trims on the write-config/inbound-command peak: `_on_mqtt_message` parses the raw frame bytes directly (MicroPython's `json.loads` takes any buffer — no decoded-string copy sitting alongside the parsed object graph at the 20 KiB inbound ceiling), and `ConfigManager._write_candidate_tmp` streams the `.tmp` write with `json.dump()` (no configuration-sized string allocation alongside the write-config peak; a mid-write failure still leaves the tolerated partial `.tmp` that the read-back re-validation decides on). `mqtt_client.py`'s publish-size error now names this client's three-byte remaining-length encoding limit (2097151) instead of the unreachable protocol maximum (268435455). `tests/test_core0_wdt.py` (new) pins the budget invariant, arming exactly once at the end of `start()` with zero startup feeds, per-pass and per-slice feeding, the no-`machine.WDT` degradation, and no arming or feeding before `start()`; `tests/test_config.py` pins accept/reject at each new bound; `tests/test_config_manager.py` proves the persistence path never builds a full serialization string; `tests/test_command_protocol.py` pins the bytes-frame parse (valid, malformed, and invalid-UTF-8 frames). `config_schema_version` unchanged.

- **Unreleased** (firmware 0.4.80): **Gated the reboot acknowledgement on a live link, and corrected the Pico 2 W RAM figure** — `core0.py`'s `_reboot_publish_due()` was the only application publish path in the run loop that did not check `is_connected()`, so a reboot pending during an outage rebuilt the entry and envelope fragment every 10 ms pass (twice per pass) only for the publish to fail immediately; the held reboot now waits for the link the same way connection logs, Core 0 responses, outbound-queue publishes, and UTC requests do. `CLAUDE.md`'s hardware notes listed the Pico 2 W as 264 KB RAM; the RP2350 carries 520 KiB SRAM (real-hardware captures observed ~333 KiB free). `tests/test_outbound_publish_pacing.py` pins the gate: a reboot pending across a scripted outage makes zero publish attempts over the outage passes, then the acknowledgement publishes on the first pass after the link returns and proceeds through the 5-second grace to `machine.reset()`. `config_schema_version` unchanged.

- **Unreleased** (firmware 0.4.79): **Made the outbound queue's heap-pressure paths re-measure the floor after every reclamation, and gave the production two-threshold soft band direct test coverage** — the heap-governed admission in `intercore.py` reclaims in two shapes that were measured inconsistently. The soft band (free heap between the hard floor and the board's preferred reserve — the Pico W's 48–64 KiB window, where the preferred reserve is not a rejection wall) reclaimed one eligible entry and immediately re-measured the floor for the append without a `gc.collect()` first, while the hard-pressure loop and the serialization-recovery path both collect after each reclamation. And the hard-pressure loop displaced its first eligible entry before ever re-measuring the floor, even when the append that had just rolled itself back (or the prior pass's collect) had already restored it — so an entry whose own rollback made it admissible was transiently rejected (empty queue, nothing to evict) or made the queue sacrifice a second retained message before the floor was checked again. The soft band now collects after a successful reclamation, and the hard-pressure loop measures the floor at the top of every pass — admitting when it is intact — before it displaces anything, so no eviction is ever decided on a heap measurement taken before the most recent collection. The behavioral change is strict: the NORMAL band (at/above the preferred reserve) is untouched, and under pressure the queue now admits whenever the floor is actually intact instead of evicting or rejecting first. `tests/test_intercore.py` now exercises the two-threshold soft band directly (its helper builds single-threshold queues, where the band is empty): the eviction-then-collect-then-admit path, an append whose own rollback reclaims enough to admit with zero evictions and zero rejections, and the soft-band rejection when nothing is eligible and the append still crosses the floor. `config_schema_version` unchanged.

- **Unreleased** (firmware 0.4.78): **Fixed the inbound MQTT frame ceiling dropping spec-valid write-config commands, and bounded what a parsed frame can cost** — `MAX_INBOUND_PACKET_BYTES` was an arbitrary 16 KiB that (a) sat *below* the largest spec-valid inbound frame: a `write-config` command carrying the worst-case valid configuration (byte-bounded identities at 4-byte code points, which serialize 3× escaped, the **character**-bounded 128-character `command_id`/`target`, the 253-byte broker address, all 16 devices, all lists at their bounds) serializes to 16,865 bytes in the conservative wire form (ASCII-escaped, default separators) — 481 over the ceiling — and was dropped at the wire layer (disconnect + recovery reconnect) without validation ever seeing it, which is exactly the round trip of `read-config`'s own worst-case output (a peer that reads the largest valid configuration and writes it back). And (b) the ceiling bounded the `sock.read()` allocation, not the parse: `_on_mqtt_message` held the decoded string alive while `json.loads()` built the object graph (≈ 3× the frame, host-measured), so a valid frame near the ceiling could put the parse peak (~65–80 KiB) at or past a Pico W's ~85 KiB steady-state free heap, and the resulting `MemoryError` — which resets the board before the QoS 1 PUBACK goes out — made the broker redeliver the same un-acked message after reconnect, so a peer that kept publishing near-ceiling valid JSON to the command topic could hold the board in a reset loop. The ceiling is now derived from the protocol: **20 KiB** = worst-case valid command (16,865) + margin, so every frame the parser can see is a bounded known constant and no spec-valid command is dropped at the wire gate. The serialized-size invariant test in `tests/test_config.py` now pins both halves of the config boundary — the worst-case read-config **response** (envelope splice included) at or under the 16 KiB outbound ceiling, and the worst-case write-config **command** (character-bounded `command_id`/`target` envelope) under the 20 KiB inbound ceiling — so a future bound growth that breaks either side fails the host suite instead of silently wedging or dropping a channel on a device. `_on_mqtt_message` also releases the decoded string as soon as the parse succeeds, so the command handler's own allocations no longer pay for a full frame, and the `MemoryError` → controlled-reset boundary remains the documented backstop for a parse transient the heap cannot meet (ARCHITECTURE.md now names the parse-peak bound and the redelivery caveat). `config_schema_version` unchanged.
- **Unreleased** (firmware 0.4.77): **Fixed a recovery path-exists check that swallowed real storage failures as "file missing"** — `ConfigManager._path_exists()` mapped *every* `OSError` from `os.stat()` to `False`, so a genuine flash/LittleFS fault (I/O error, `LFS_ERR_CORRUPT`, `ENOTDIR`, ...) was indistinguishable from an absent file. `ConfigManager.recover()` uses those booleans to choose the authoritative artifact and then delete/rename on that premise: a stat fault on `config.json` read as "absent" could promote a valid `config.json.old` over a file the code could not even stat, or — with no valid artifact — fail boot with `ConfigError("... all missing or invalid", code="unreadable_file")`, discarding the original I/O error. The check now maps only `ENOENT` to `False`; any other `OSError` propagates with its error context intact, so recovery (and the HOT commit/rollback/restore paths that share `_path_exists`) cannot select an artifact on a false premise. On-device `os.stat()` raises `ENOENT` for a missing path (`mp_raise_OSError(LFS_ERR_NOENT)` → `errno.ENOENT = 2` in the rp2 LittleFS glue) and `EIO`/`84` for real faults, and the same numeric comparison holds under CPython, so the behavior is identical on host and hardware. Boot-path failure shape is unchanged (a non-`ENOENT` stat now escapes `recover()` at `main.py:62` to the same visible-traceback + soft-reset path an invalid config already takes — but naming the actual error). Two new host tests pin the mapping (ENOENT → absent, non-ENOENT `OSError` → propagated). `config_schema_version` unchanged.
- **Unreleased** (firmware 0.4.76): **Fixed the configuration string bounds not enforcing the byte-size invariant** — `source`, device `id`/`name`/`sensor_type`, and (unbound until now) `mqtt_broker_ip_address` were length-checked in characters (or not at all), while the safety contract they serve is expressed in UTF-8 bytes (`MAX_OUTBOUND_MESSAGE_BYTES = 16 KiB`). A valid configuration at the permitted maximums (16 devices, 64-character fields of 4-byte code points, maximum topics and reconnect arrays) serialized its read-config response at 40+ KiB under the serializer's escaped output — 2.5x the ceiling — and a single ~15 KiB `mqtt_broker_ip_address` (no bound at all) crossed the ceiling on its own, so `validate_config()` could certify a configuration whose read-config response is permanently unsendable (answered only by the bounded `response_too_large` substitute) while the `config.py` comments asserted the opposite. The four protocol-scale fields are now bounded in **UTF-8 bytes** (`len(value.encode("utf-8"))`, error messages now say "bytes"), `mqtt_broker_ip_address` gains a new **253-byte** bound (DNS hostname maximum — `socket.connect()` resolves hostnames, so IP-only bounds would have rejected legal values), and a serialized-size invariant test pins the property: the worst-case valid configuration (every string field at its byte bound in the worst serialized form, every list at its entry bound, all nine `system-information` sections) must still serialize its read-config response — including the Core 0 envelope splice — at or under `MAX_OUTBOUND_MESSAGE_BYTES`, so a future field or driver string that breaks it fails the host suite instead of wedging read-config on a device. Tightening-only validation change — the accepted set only shrinks (over-long multibyte values that previously validated are now rejected; no previously invalid value becomes valid) — so `config_schema_version` is unchanged.
- **Unreleased** (firmware 0.4.75): **Fixed a valid configuration silently disabling the entire MQTT command path** — `validate_config()` checked each of the eight `mqtt_topic_*` channels independently but never compared them against each other, so a configuration with `mqtt_topic_command == mqtt_topic_info_response` booted, connected, synchronized UTC, and published telemetry/health (reporting `healthy`) while inbound dispatch — which matches delivered topics by exact equality and checks the info_response branch first — dropped every command envelope silently, and since both keys are `REBOOT_REQUIRED` and `write-config` runs candidates through this same validator, such a configuration could be committed and take effect after reboot with the command channel (including `write-config` itself, the repair channel) permanently dead. `validate_config()` now requires all eight channel names to be **pairwise distinct** (`invalid_value`, naming the colliding keys and the shared topic), which also closes the secondary exposure the shared check covers: MQTT 3.1.1 delivers a client's own publications back to its subscriptions, so a channel name shared with any locally published topic re-delivered every own publication inbound (worst case, command aliased to telemetry — decoded on a 256 KiB heap every read loop and dropped at the `message_type` gate).
  - Tests: the fatal command/info_response pair rejected with the exact message, all 28 remaining channel pairs rejected, and a renamed-but-distinct baseline accepted (`tests/test_config.py`). `CONFIG_SCHEMA_VERSION` is unchanged — the rule constrains values, not the schema shape; shipped configurations with distinct topics validate as before.
- **Unreleased** (firmware 0.4.74): **Fixed the deterministic startup→reset loop — the first post-startup publish (the startup log) hit a silent `MemoryError` on a fragmented heap, and the controlled-reset boundary restarted the board into the same failure** — `_publish_entry()` built the spliced envelope as `b"".join((body[:-1], b",", fragment, b"}"))`, allocating the *entire* frame as one contiguous buffer at the worst possible moment: the startup log is the largest message in the normal profile (~3.5 KiB with the deployed configuration), and it is published right after the startup imports, where `gc.collect()` has freed ~42 KiB of startup garbage as scattered holes and ~46 KiB of long-lived import objects are interleaved into them. With ~67 KiB of heap free in total the largest free block was smaller than the frame, so the allocation failed deterministically (instrumented trace: `core0.start() returned 77008` → `gc.collect() 119248` → `core1 imported 72848` → `thread started 68416` → `run() first pass 68144` → death; Core 1's `put()` had admitted the very same serialized startup log seconds earlier, proving the heap was just over the cliff). The `MemoryError` is silent on the broker by design (the handler must not allocate, so the reset can always run), so the loop presented as ~15.5 s boot cycles with no visible cause; MQTT-marker instrumentation masked the fault 9/9 (allocation-pattern perturbation) and a `gc.collect()` line did not fix it (collection does not compact). The splice now happens at the wire as segment writes — a zero-copy `memoryview` of the body minus its closing brace, then `,`, the fragment, and the brace as separate `sock.write` calls — so the broker receives byte-identical frames (TCP is a byte stream), the `MAX_OUTBOUND_MESSAGE_BYTES` ceiling is still enforced against the final wire length before any frame byte goes out, and the largest new contiguous allocation in the publish path is the ~300-byte envelope fragment instead of the frame. Also fixed a second boot wedge demonstrated on the same path: `_drain_startup_mqtt_work()` re-armed its 2-second grace deadline on every loop iteration, so a dead or blackholed link — whose publish fails fast (~100 ms) and leaves the same head log pending — could never expire the deadline, and boot wedged inside `start()` retrying the same log indefinitely (observed: 8+ minutes of `Connection log publish failed, retrying: MQTT is not connected`). The `MemoryError` handler performs no allocation (it resets immediately, because a diagnostic line would itself be an allocation on an exhausted heap and a raising handler would defeat the reset), while the generic `Exception` handler logs one diagnostic line first (safe, since by construction the failure is not heap exhaustion) and then resets; `machine.reset()` never returns on hardware, so neither handler falls through. Core 1 gating is preserved — if `start()` fails, the Core 1 thread never starts. `core0.py` docstrings updated accordingly (a `MemoryError` propagating out of `start()` now terminates in this boundary as a controlled reset). Failure-path behavior change (no `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.32 → 0.4.33).

- **Unreleased** (firmware 0.4.31 → 0.4.32): Added Core 0-owned duplicate command suppression. `command_id` is the idempotency key — exact, case-sensitive, and opaque (never normalized) — and the first accepted use of an ID owns it until eviction regardless of command name, payload, or target casing. Core 0 retains the 16 most recently accepted command IDs (`core0._RECENT_COMMAND_ID_CAPACITY`) in a fixed-size RAM FIFO, and a command whose ID is still retained is silently ignored — no execution, no Core 1 event admission, no response, and no change to a pending reboot — covering Core 0 commands (reboot) and Core 1 commands (get-details) alike. The check runs at command ingress, after topic/`message_type`/target/identity validation and before schema/payload validation, reboot handling, and event admission: a non-matching target or an invalid `command`/`command_id` keeps its existing early return and consumes no cache entry, a duplicate receipt neither refreshes the entry's FIFO position (last accepted distinct IDs, not LRU access order) nor triggers a response replay (no prior response is retained or resent), and an ID evicted by 16 newer distinct IDs may be processed again. The cache is RAM-only — reboot clears it and it is never persisted to flash — and a suppressed ID emits a DEBUG-only diagnostic, not a production warning. No `config_schema_version` or `message_schema_version` change; `FIRMWARE_VERSION` 0.4.31 → 0.4.32.

- **0.4.30**: Made a permanently oversized command response unable to stall the Core 1 command channel. - **0.4.26**: Replaced the count-bounded queues with heap-reserve-bounded queues. The fixed capacity rules (outbound 16-entry count + 32 KiB aggregate byte budget; event 4-entry count) are gone: both FIFO lanes are now admitted against the global minimum free-heap reserve, sourced from `hardware.py` (64 KiB Pico W, 128 KiB Pico 2 W) — the single source of truth for queue memory safety, not deployment-configurable. `InterCore` now takes `minimum_free_heap_bytes` (from `main.py`'s early `detect_hardware()`) and creates one shared heap-admission lock, passed to both queues, that serializes the heap measurement, the pressure-path `gc.collect()`, and the eviction/admission decision — because the MicroPython heap is global to both cores. Outbound admission: fast path admits with no garbage collection when `gc.mem_free() >= reserve`; the pressure path collects once, and if the reserve is still not restored evicts the oldest entry in the least-important eligible queued class (only when the incoming entry is at least as important), reclaims, and rechecks — repeating until the reserve is restored or nothing eligible remains — then admits or rejects. The in-flight QoS 1 entry is never an eviction candidate, and priority/oldest-first semantics are otherwise unchanged. The event queue uses the same reserve and lock but never evicts an admitted event (discrete control operations): under pressure the new event is rejected and Core 0 reports the new `intercore_event_queue_memory_pressure` error code. - **0.4.21**: Made the outbound byte budget account for the in-flight entry's retained bytes, so the budget now caps ALL payload bytes the outbound queue retains, not just the queued FIFO. The in-flight entry is popped out of the FIFO by `take()` and held until its PUBACK (`complete_in_flight`), so its payload bytes stay resident the whole time — but `take()` subtracted them from the byte count the moment the entry moved in-flight and `complete_in_flight()` never re-added them. The budget therefore capped only the queued FIFO: a 16 KiB in-flight payload plus a full 32 KiB of queued payloads could be resident at once (48 KiB) while `outbound_queued_bytes` reported only 32 KiB, and admission kept granting the full 32 KiB of queued room on top of whatever was in flight. Now `take()` leaves the entry's bytes counted, `complete_in_flight()` releases exactly the completed entry's bytes, and eviction subtracts queued entries as before — the in-flight payload consumes budget for as long as it is retained. This tightens the worst-case retained payload from 48 KiB to 32 KiB and makes the two budget views consistent: `outbound_queue_depth` already included the in-flight entry, and `outbound_queued_bytes` now does too. `outbound_queued_bytes` (health and startup log) can now read slightly higher while an entry is in flight; `outbound_max_queued_bytes` is unchanged. - **0.4.20**: Made a Core 0 command/reboot response retry the same wire document, not just the same sequence identity. 0.4.17 made `(runtime_id, sequence)` a reliable unique event identity by claiming the sequence before the first transmission attempt and stamping it on the logical object so a retry reuses it — but for Core 0's own retryable responses (the pending command responses and the pending reboot) the identity was preserved while the *content* was not: `_publish_core0_command_response()` rebuilt the message (re-capturing `uptime_ms` and `timestamp`) and re-serialized it on every attempt, so an ambiguous QoS 1 failure (the PUBLISH reached the broker but the PUBACK was lost) followed by a retry put two packets with the *same* `(runtime_id, sequence)` on the wire carrying *different* documents (differing `uptime_ms`/`timestamp`). A downstream deduplicator keyed on that identity could then discard one of two differing documents depending on arrival order. Queued telemetry never had this problem because its pre-serialized bytes stay attached to the same in-flight queue entry. - **0.4.19**: Made the disposal of a failed MQTT client bounded too, closing the last unbounded write on Core 0's network path. 0.4.16 bounded the QoS 1 PUBLISH frame writes and the PUBACK wait, but the cleanup of the client left behind after such a failure was not: `Mqtt._close_old_client()` — the first step of every `connect()` attempt, i.e. of every reconnect — called `MQTTClient.disconnect()`, which unconditionally wrote an MQTT DISCONNECT frame. After a failed bounded exchange, the exchange's `finally` had already restored the socket to infinite-blocking mode, so that DISCONNECT write into the already-failed link had no deadline: on a blackholed link (TCP up, sends not draining) it wedged Core 0 inside `sock.write()` forever, and with Core 0 wedged its Core 1 heartbeat watchdog (0.4.9) could never run either — the same P1 class 0.4.16 fixed for the PUBLISH itself, one step later in the failure chain (publish stalls → bounded timeout → socket restored to infinite blocking → reconnect → unbounded DISCONNECT write → permanent wedge). - **0.4.17**: Made the wire `sequence` reliable across an ambiguous QoS 1 failure. The sequence was consumed only after a successful PUBACK, so in the ambiguous case — the PUBLISH reached the broker but the PUBACK was lost — the number was never consumed and was handed out again: a `mqtt_connection_established` log published after the reconnect took the in-flight telemetry's sequence (a `(runtime_id, sequence)` collision on the wire), and the telemetry retry then took a still-newer one, so the same logical sample appeared under two identities and an unrelated message reused the sample's number. - **0.4.15**: Made `MemoryError` propagation consistent on the Core 0/Core 1 message paths. - **0.4.14**: Stopped the telemetry scheduler from replaying missed boundaries as catch-up reads. When a device read stalled long enough to cross one or more `read_loop_sec` boundaries, the deadline advanced by a single interval per pass, so the loop fired an extra read almost immediately — and another, until it caught up: a burst of near-identical current samples, JSON work, and queue admissions landing right after the overload. Telemetry is a current sample, not a replayable record, so a stall cannot reconstruct the missed samples; the scheduler now performs the current sample once and skips directly to the next future boundary — the same missed-boundary policy the health scheduler already used. The skip is evaluated against a clock re-read after the read completes, because the loop's captured clock is stale by however long the read took and would otherwise under-advance and leave a catch-up read for the next pass. Outage buffering is unchanged (an MQTT outage still queues telemetry rather than dropping it); this only changes the pathological slow-read case. Static behavior change (no `config_schema_version` change).

- **0.4.13**: Eliminated the double serialization on the publish path. A queued message was serialized by its sender and then, on Core 0, decoded, parsed back into a dict, merged with Core 0's envelope fields, and re-serialized as a whole document (`dict → str → bytes → queue → str → dict → str → MQTT`): the message body was serialized twice, and the transient allocations, CPU, and fragmentation risk accumulated exactly where the queue was supposed to improve memory predictability. The contract is now: the sender carries its complete message — including `uptime_ms` and `timestamp` (null when UTC is unsynchronized) — and must not carry any envelope key at the top level (`sequence`, `runtime_id`, `source`, `firmware_version`, `message_schema_version`); Core 0 injects those five members at publish time by splicing them into the stored serialized object before its closing brace. The payload is never decoded, parsed, or re-serialized on the publish path, so publishing allocates only the small envelope fragment plus the assembled frame. The wire format is unchanged (same top-level keys, same Core 0 values) and the queue still stores immutable pre-serialized bytes — the frame is a fresh allocation, the entry is untouched. Core 1 no longer pre-embeds `runtime_id`/`source`/`firmware_version`/`message_schema_version` (they were always overwritten by Core 0 anyway), and the health/startup-log `timestamp` is computed from the shared UTC snapshot instead of being left null for Core 0 to fill (which required the parse it could no longer afford). Static behavior change (no `config_schema_version` change).

- **0.4.12**: Bounded the inbound MQTT packet size. `wait_msg()` now rejects a PUBLISH whose remaining length exceeds `MAX_INBOUND_PACKET_BYTES` (16 KiB — the same MCU-scale ceiling as the outbound limit) *before* allocating its payload: previously `sock.read(sz)` was handed whatever the broker's remaining-length field claimed, and a broker-side bug publishing an oversized command/info response could request an allocation large enough to exhaust the Pico W's RAM (no hostile traffic required). An oversized frame — like a fifth remaining-length byte (an MQTT protocol violation that was previously an unbounded read loop) — now closes the socket and raises `MQTTException`, which the `Mqtt` layer turns into a marked disconnect and Core 0's existing recovery path reconnects, instead of trying to buffer or drain the corrupt stream. - **0.4.11**: Fixed the MQTT receive path parsing incoming packets in non-blocking socket mode. `check_msg()` now decides *readiness* with a non-blocking `select` poll — one readable byte means a packet has started; nothing returns `None` immediately and leaves the socket mode untouched — and only then parses the packet on a blocking-with-finite-timeout socket bounded by `mqtt_broker_response_timeout_sec`. Previously the whole multi-byte parse ran non-blocking, and because MicroPython documents that `read(n)` may return fewer bytes than requested in non-blocking mode, a PUBLISH split across TCP reads could short-read its topic or payload and deliver a corrupt frame (or raise a spurious disconnect) instead of waiting for the rest of the packet. Now a link that stalls after the first frame byte surfaces as a bounded timeout into the existing recovery path, and a ready packet is always fully read. `wait_msg()` and the bounded-wait invariants are otherwise unchanged; `check_msg()` now installs and restores its own finite timeout like `publish`/`ping`. Static behavior change (no `config_schema_version` change).

- **0.4.10**: Made startup verification self-healing to match the (already) unbounded connect loops. Previously the QoS 1 probes and UTC sync were the only fail-fast steps: a single transient blip after connection — a dropped PUBACK on a probe, or a brief UTC-server outage across the 3 bounded attempts — raised `RuntimeError` out of `core0.start()`, exited `main()`, and left the device stopped until a physical reset, even though a broker that was *never* reachable would have looped forever. `start()` now keeps the verification steps (probe #1 → drain → 5 s wait → probe #2 → UTC) in a new `_verify_startup_contract()` pass inside a retry loop: on any pass failure it drops the MQTT session (`mark_disconnected()`), re-establishes the network, and retries the whole pass, reusing the existing `mqtt_reconnect_delays_sec` backoff. Core 1 stays gated because `start()` has not returned and `_network_stack_ready` is set only after a clean pass; a `MemoryError` still propagates (fail-fast) so an out-of-memory device is not looped. Static behavior change (no `config_schema_version` change).

- **0.4.9**: Core 0 became the independent consumer of the Core 1 liveness heartbeat, closing the P1 failure mode where a dead or wedged Core 1 thread (an unhandled `MemoryError`/`Exception`) wedged the whole sensor — telemetry and health silently stopped, a dead Core 1 could not build the health message that would report `core_1_inactive`, and Core 0 kept running indefinitely with no recovery. The Core 0 run loop now checks `core_1_activity_ms` first on every pass (`_watch_core_1_heartbeat` in `core0.py`): before any stamp exists (Core 1 has not started) the check is a no-op, so the unbounded startup connect loops are unaffected; once a stamp exists, age at or beyond `_CORE_1_HEARTBEAT_STALE_TIMEOUT_MS` (30 s — more than six missed 5 s refreshes, and below the 60 s `core_1_inactive` diagnostic threshold) logs FATAL and calls `machine.reset()`. Static constant (no `config_schema_version` change).

- **0.4.8**: Made the outbound message/queue limits MCU-safe. The per-message ceiling dropped from 128 KiB to 16 KiB (`message_serializer.MAX_OUTBOUND_MESSAGE_BYTES`) — the check runs after `json.dumps()` + UTF-8 encode, so the object graph, serialized `str`, and encoded `bytes` are all resident at once and a 128 KiB payload could not be admitted safely on a Pico W; 16 KiB bounds a single message's transient peak (~48 KiB) with margin over the largest legitimate message (the startup log). `OutboundQueue` is now bounded by BOTH entry count and an aggregate queued-byte budget (`DEFAULT_MAX_OUTBOUND_QUEUED_BYTES` = 32 KiB), so 16 retained payloads can no longer exhaust heap on their own; admission enforces both budgets and only evicts when it frees enough room (by count or bytes), never dropping a valid entry to admit one that would not fit. Both bounds are static constants (no `config_schema_version` change); `OutboundQueue.status()` now also reports `queued_bytes` and `max_queued_bytes`.

- **0.4.7**: Fixed the MQTT handshake blocking indefinitely: `Mqtt.connect()` now passes `mqtt_broker_response_timeout_sec` to `MQTTClient.connect()`, bounding the CONNACK wait — and, since `subscribe()` inherits that socket timeout, both SUBACK waits. A broker that accepts the TCP connection and then stops responding now fails the connect attempt (retried with the reconnect backoff) instead of wedging Core 0 forever; the socket returns to normal blocking mode once both subscriptions succeed.

- **0.4.6**: One shared normal-runtime scheduling epoch for all periodic Core 1 work. `normal_runtime_start_ticks_ms` is captured exactly once, immediately after `system_startup_completed` is admitted to the outbound queue; both the telemetry deadline (`anchor + n × read_loop_sec`) and the health deadline (`anchor + n × health_interval_sec`) derive their fixed boundaries from that anchor. Telemetry and health remain independent schedulers (shared epoch, no execution dependency); neither deadline derives from the other. `boot_ticks_ms` remains the boot-lifetime reference for uptime (`uptime_ms`) and startup-duration measurement only. Reconnects, UTC resyncs, and device reinitialization never reset the anchor; only a reboot creates a new one. Health outage policy is unchanged (missed intervals skipped, never replayed); telemetry outage buffering is unchanged.

- **0.4.5**: Health scheduling anchored to boot time: `health_interval_sec` now defines fixed uptime-based boundaries from firmware boot (60s interval → first health at ~60s uptime, then 120s, 180s, ...). The immediate post-startup health message is removed; boundaries missed during startup or an MQTT outage are skipped, never replayed; deadlines advance from the previous boundary so processing delay cannot accumulate drift.

- **0.4.4**: Fixed UTC retry throttle blocking its own prompt retry: a malformed-but-reachable time-server answer now re-keys the retry backoff to ~0.5s (previously the 30s interval, measured from the original send, blocked the resend even though the server had just answered); a silent server still gets the full 30s throttle.
